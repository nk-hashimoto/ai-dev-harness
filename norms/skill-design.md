# Skill の書き方(新規作成・改訂のときに読む)

> Skill を新規作成する、または既存 Skill を直すときに開く。既存と重複していないかは `~/.claude/skills/` と対象プロジェクトの `.claude/skills/` を確認する。

## 命名と description

**利用できる環境なら、公式の `skill-creator` に任せる。** description のトリガー精度の測定・最適化まで面倒を見る。無い環境向けに最低限だけ挙げる。

- **名前は実際の対象範囲を過不足なく表す。** 対象より広く読める名前を付けると、後から見た人(自分を含む)が適用範囲を誤解する
- **description に、対象が増えると陳腐化する固有名詞(具体的なファイル名・テスト名)を書かない。** description は呼ばれるかどうかを決める文なので、書いた時点の具体例に固定すると、対象が増えたときに**本来マッチすべき場面で選ばれなくなる**。具体例の列挙は本文に置けばよく、description 側だけの制約

## 起動条件

**前提**: スキルは description がシステムプロンプトに載るので、**既定ではモデルが場面を判断して自分で起動する**。明示的に呼ばれるのを待つわけではない。下に書くのはすべて**その判断に効かせるための指示**であって、仕組みの説明ではない。

**既定は「description に書いた場面で呼ばれる」。** それで誤解が生じないなら、追加の宣言は要らない。

**明記が要るのは次の2つ。** どちらも **description と本文の冒頭の両方**に書く(片方だけだと、呼ぶ側と読む側のどちらかに届かない)。

- **常時実行にする** — 呼ばれるのを待たずに走る。書かなければ、呼ばれるまで走らない
- **自動起動させない** — 他の作業の最中に「念のため」で走りうる性格のもの(検証をもう一巡させる / 棚卸し / 計画立案)。書かなければ勝手に始まり、本題が逸れる

`skill-creator` はこの判定をしないので、必ず自分で決める。

判定は「**そのモデルが指示なしでやることと二重になるか**」ではなく、「**読む対象が有界に決まっているか**」で行う。前者はモデルの自己申告に依存し、実際には「自前でやっている」と思っているのに守れていないことが起きる。

- **読む対象が決まっている**(表・チェックリストで引ける) → **常時実行にしてよい**。開放的な再検証にならず、下限を担保できる
- **開放的**(「もう一度確かめろ」「気になるところを見ろ」) → **明示的に呼ばれたときだけ動く**と書く。何度でも走らせられてしまい、コストだけ増える
- **それ自体が独立した作業**(棚卸し・計画立案) → 同上。本題の最中に始まると脱線する
