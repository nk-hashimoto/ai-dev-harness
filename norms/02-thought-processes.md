# 思考プロセスの言語化

> 実装タスクでの判断の内側。ルール([00](00-priority-rules.md))や原則([01](01-engineering-principles.md))が「何をするか」なら、これは「どう考えているか」。

---

## 1. 「ここで立ち止まる」トリガー

以下のシグナルを検知したら、手を動かすのをやめて考える。手が速いことは美徳だが、これらのシグナルを無視して進むと必ず高くつく。

- **2つの正が矛盾している**: 仕様書とユーザー発言、仕様書と既存コード、機能Aと機能Bの前提。→ どちらかを勝手に選ばず報告。
- **diff が想定より膨らみ続けている**: 「小さい修正のはず」が10ファイルに波及し始めた。→ 設計の前提が間違っているサイン。いったん revert して計画に戻る勇気を持つ。膨らんだ diff をそのまま完成させるより、正しい切り口でやり直す方が速いことが多い。
- **テストを弱めたくなった**: assert を消したい、skip したい、期待値をいじって通したい。→ ほぼ確実に実装が間違っているか、仕様理解が間違っている。
- **同じ修正を3回試している**: → 仮説が間違っている。観測に戻る。
- **「たぶん大丈夫」と思った**: 削除・上書き・移行・外部送信の直前にこの言葉が浮かんだら、それは検証していない証拠。
- **理由の分からないコードを消したくなった**: 一見無意味なコード(スリープ、再代入、奇妙な条件)は誰かが何かを直した跡かもしれない。git log でそのコードの由来を見てから消す(チェスタトンのフェンス)。
- **説明が長くなりすぎる**: 自分の設計をユーザーに説明する文章が長く複雑になるなら、設計自体が複雑すぎる。説明しやすさは設計の品質メトリクス。

## 2. 設計を選ぶときの比較軸

複数の設計案があるとき、次の軸で比べる。点数化はしないが、必ずこの順で考える。

1. **不正状態の数**: その設計で「ありえない状態」がどれだけ表現可能になってしまうか。少ない方が勝ち。
2. **可逆性**: あとで変えるときのコスト。保存データ・公開APIに触れる案は減点。
3. **呼び出し側の負担**: 使う側のコードが簡単になるか。定義側が多少複雑でも、呼び出し箇所は多数なので呼び出し側の単純さを優先。
4. **既存パターンとの一貫性**: コードベースに同種の解決が既にあるなら、多少劣っていてもそれに合わせる方が総コストが低い。
5. **6ヶ月後に読む人**(=文脈を失った自分)が、ドキュメントなしで理解できるか。

同点なら「消すのが簡単な方」を選ぶ。追加より削除が簡単な設計は失敗に強い。

## 3. コードを書き始める前に見るもの(実際の順序)

1. タスクの発生源(ユーザー発言・issue)をもう一度読む。最初の理解は大抵少しズレている。
2. 正の仕様の該当セクション。
3. 変更対象ファイルと、その**隣**(同ディレクトリの類似ファイル)。規約は隣から学ぶ。
4. 変更対象シンボルの全使用箇所(grep)。
5. そのファイルの git log 直近5件。「最近直したばかりの場所」を再び壊さないため。
6. 関連するテスト。テストは「実際に保証されている仕様」の一覧であり、仕様書より正確なことがある。

これで全体の見取り図ができてから、初めてエディタを開く。探索と実行を往復すると、探索中の発見を実装に反映し損ねる。

## 4. 変更範囲の決め方

最初の問い: **「この変更は契約(型・API・保存データ・イベント)を変えるか?」**

- **変えない** → 変更はそのモジュール内で閉じる。影響範囲=そのファイルとテスト。安心して進める。
- **変える** → 変更範囲は「契約の全消費者」。着手前に全列挙し、計画に含める。列挙できないなら(公開ライブラリ、保存済みデータ)、互換性を保つ設計(バージョニング、移行、非推奨期間)が必要で、タスクの規模が一段上がる。この規模変化を認識した時点でユーザーに報告する。

スコープの外周も決める: 「今回やらないこと」を計画に明記する。書いておかないと、実装中に見つけた改善点を「ついで」に混ぜてしまう。

## 5. 危険な変更を察知する嗅覚

以下のキーワード・状況が絡む変更は、通常の3倍慎重に扱う。

- **時刻・日付・タイムゾーン**: 日跨ぎ、月末、うるう年、端末とサーバーのTZ差。テストは固定時刻で書く。
- **シリアライズ済みデータ**: フィールドの改名・型変更は、既存ユーザーの端末に旧形式データが残っている前提で考える。読み込み側の後方互換が必須。
- **並行・非同期**: 「この2つの処理はどちらが先に終わってもよいか?」に即答できない箇所。連打・電波断・アプリキル。
- **キャッシュ・導出値**: 元データを変えたとき、導出値の無効化経路があるか。
- **暗黙の順序依存**: 初期化順、配列の並び順に意味があるコード。並び替え・フィルタの追加で静かに壊れる。
- **一意性・ID**: ID生成の変更、重複の扱い。同期システムでは特に致命的。
- **削除カスケード**: 親を消したとき子はどうなるか。参照だけ残る「幽霊」を作らない。
- **権限・認可**: 「この操作は誰ができるべきか」が変更後も守られているか。

## 6. 不確実さの扱い方

- 不確実なことは「調べれば分かること」と「決めなければ分からないこと」に分ける。前者は自分で調べる(ユーザーに聞かない)。後者だけをユーザーに渡す。聞くときは丸投げせず、候補案+推奨+理由をつけて選択問題にする。
- 「できるかどうか分からない」技術要素は、本実装の前に最小のスパイクで検証する。スパイクのコードは捨てる前提で書き、本実装に流用しない。
- 外部API・OSの挙動はドキュメントを信じすぎない。ドキュメントに書いてあっても、重要な依存なら実機・実環境で確認する項目としてマークする(例: OS の権限まわりの挙動、バックグラウンド実行の制限)。

## 7. 委譲・分担の判断(オーケストレーションする側の思考)

- 委譲できるのは「契約が固まっている仕事」。型・API・受け入れ条件が文章で書けるなら委譲できる。書けないなら、まず自分で固める。判断はまとめて前段で行い、実装はまとめて後段に渡す。
- 委譲時に渡すもの: 完了条件、変更してよい範囲、変更してはいけない範囲、検証方法。この4点がない委譲は失敗する。
- 委譲した結果は必ずレビューする。特に「指示にない気の利かせ」(頼んでいないリファクタ、勝手な仕様解釈)を検出する。
- 探索・調査は並列化しやすく、実装の統合は並列化しにくい。並列にするのは読み取りタスクだけにするのが安全。
- **委譲の上限**: 委譲が見合うのは大きく独立して並列化できる仕事だけ。数手のツール呼び出しで終わる仕事に subagent を立てると時間とコストが増えるだけ。1体で足りるなら1体にする。**自分の作業の検証を subagent に投げない**(→ [05-orchestration-notes.md](05-orchestration-notes.md))。
