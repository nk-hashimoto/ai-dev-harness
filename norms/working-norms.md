# 作業規範(汎用 CLAUDE.md — Sonnet/Opus 向け)

> プロジェクトを問わず適用する作業ルール。プロジェクト固有の CLAUDE.md と併用し、矛盾したらプロジェクト側を優先する。
> 詳細な理由・背景は同ディレクトリの 00〜04 を参照(このファイルは運用ルールの凝縮版)。
> 各項目は**満たすべき結果**の列挙であって手順の指定ではない。実行モデル別に指示をどう書くかは [05-orchestration-notes.md](05-orchestration-notes.md)(呼び出し側向け)。

## 着手前(必ずやる)

1. 正の仕様を特定する(spec / CLAUDE.md / ユーザー発言)。矛盾があれば着手前に報告する
2. 完了条件を1文で言えるか確認する。言えなければ、自分の解釈を明示して確認を取る
3. 同種の既存実装を1つ読み、その規約(命名・エラー処理・配置)に従う。自分のスタイルを持ち込まない
4. 変更対象シンボルを grep し、影響範囲(呼び出し元・テスト・保存データ・ドキュメント)を列挙する
5. 着手前のテスト実行でベースラインを取る(着手前から red なら自分の変更のせいでないと確定させるため。既に green と分かっているなら省略してよい)

## 作業中

- **探索→計画→実行→検証を分離する。** 読みながら書かない。計画からズレ始めたら実行を止めて計画に戻る
- **検証するときは、見ている結果が「自分の変更後のもの」かを先に確かめる。** キャッシュ・スナップショット・ビルド成果物・再起動していないプロセスは、平然と古い版の結果を返す。版を識別できる印(設定に埋めたマーカー・ビルドID・mtime)を出力に含め、それを確認してから中身を読む。**古い版の成功を新版の成功と読み違えると、動かない実装を「動いた」と判断して先へ進む**(実例: 動かない認証方式を、キャッシュ済みログに残っていた旧版の成功と誤読し、正しい仮説を捨てた)
- **「全部見た」と言う前に、それを数えた網の妥当性を先に確かめる。** grepのパターン・範囲の切り方・開始マーカーは**それ自体が仮説**で、外れていても「0件」という異常なしの顔をした結果を返す。数える前に「この網が拾えない書き方はあるか」を1度問い、1つでも挙げられるなら網を直してから数える。理由: **掃引の失敗は痕跡を残さない** — エラーも不合格も出ないので、報告した側も受け取った側も網羅したと信じたまま次の判断を積む(例: シートの開始マーカーで範囲を切って「旧トークンの残数0件」と報告したが、マーカーに合わない書き方のシートが2つあり、同じ部品5箇所のうち3箇所しか直っていなかった。同じ形の誤りが1タスク中に3回起きた)。
  **この問いは、自分が今書いている網にも掛かる** — レビュー対象の網には当てられていても、同じターンで自分が書いている網には当てそこねる(例: 「網を作る → 次のレビューがその網の穴を見つける」を4ラウンド繰り返した。4件とも網を書いた直後に1度問えば1ラウンドに畳めた)。  
  **網が成果物として残るとき**(検査・テストとして置く網)**は、挙げた形を doc に書いて済ませない** — 網を直すか、**読めないと分かる形で落とす**かのどちらかにする。doc は網が変わったときに黙って嘘になり、次に読む人は「ここまでは読める」と信じて穴の上に判断を積む。  
  **抽出した件数を閾値で守るなら枝ごとに数える** — 合算の下限は、片方の枝が全損してももう片方の件数で緑のまま通る(実例: 実在95件のリテラル枝を丸ごと殺しても、架空80,626件を含む合算が下限を超えて全て緑だった)
- 1コミット = 1論理変更。動作変更とリファクタリングを混ぜない
- 依頼されていない変更(ついでのリファクタ・整形・別バグ修正)は実施せず、報告の「提案」欄に回す
- **検証・確認の都合で製品の仕様を決めない。** 「この方式なら手元で照合できる」「テストが書きやすい」は実装方式の判断材料にはなるが、**ユーザーに出るものの形**を決める根拠にはならない。検証手段が制約になるなら変えるのは検証手段の側で、それが無理なら「検証しにくいと承知でこの仕様を採る」と明示して別に決める。検証の都合は開発中しか存在しないのに、決まった仕様は出荷後も残る(例: ある入力欄を既製の部品ではなく自前で作った根拠が「そうすればテスト環境で見た目を照合できる」だった。照合手段の制約が製品のUIを決めていた)
- 状態・フラグ・モードを追加する前に「この状態を作らずに済む構造はないか」を1分考える。導出できる値は保存しない
- **常に一緒に現れる値の組が「片方だけでは不正」という制約を表しているなら、その組だけを共通型に切り出す**(例: 金額と通貨 — 金額だけあって通貨が無い値を作れなくする)。**上位の型は統合しない** — 同じ組を含んでいても、エンティティか埋め込み値か・寿命・同期の扱いが違えば別概念で、基底型を共有させると片方にしか意味のない操作がもう片方にも通る。共通化するのは「制約」であって「見た目が似ていること」ではない。**型に限らずスタイル・コンポーネント・設定も同じで、判定は「常に同じであるべき」と正のドキュメントが定めているかで行う** — **2箇所の中身がたまたま同値であることは根拠にならない**(例: 2つの画面のフォームの余白が同じ値だったので共通コンポーネント化しようとしたが、揃えるべきという規約はどこにも無かった。値を共有すると片方の画面の要件が変わったときにもう片方が黙って動く)
- 型・API・DBスキーマ・保存済みデータ形式を変えるときは、全消費者を列挙してから着手。永続化済みデータの形式変更は後方互換なしにやらない
- **ある性質を支えていた仕組みを別の仕組みへ移したら、移った先が要求する前提を守る構造も同時に置く。** 移し替えは「同じ性質を別の方法で得た」ように見えるが、たいてい**新しい前提を持ち込んでいる**。移す前の仕組みが暗黙に満たしていた条件を書き出し、移した先で誰がそれを保証するのかを言えるようにする。言えないなら、それは移し替えではなく穴を開けただけ(例: 書き込みの排他をDBの接続分離からアプリ側のキューへ移したとき、排他は「キューが1本であること」に依存するようになった。接続は共有されるのにインスタンスは複数作れたので、キューだけが割れて排他が消えた)
- **通常経路の横に別経路を足したら、通常経路が持っていた不変条件・ガード・導線を1つずつ照合する。** 上の項が「移し替え」なのに対し、こちらは元の経路を残したまま**横に足す**ケース。新しい経路は例外的な入力のために作るので、正常系では当たり前に効いていた守りが素通しになる。**その経路が「復旧のための道」であるほど危険** — 辿ると壊れる(例: 壊れた行を含むレコードを degraded として別扱いする経路で、通常経路にあった「最後の1件は消せない」ガードが無く、復旧操作で対象が到達不能になり、削除を促す文面から遷移先へのリンクも無かった。同じ形の欠陥が4回続いた)。**足した防御そのものが、防ごうとした失敗形を持っていないかも同じ軸で確かめる**(例: 設定の取りこぼしを塞ぐコードが、引数省略時にその設定を消していた)
- **仕組みを変えたら、その仕組みの振る舞いを述べている記述も洗う。** ドキュメントにも消費者がいる。変更点だけを見ていると説明が黙って嘘になる — 実装は正しいので動作を見ても気づけない。**規範やSkillの手順書が古いまま残ると、次のセッションがその嘘に従って動く。** 洗う対象は仕組みの名前を出している記述に限らない(実例: lint の網を広げたとき、設定ファイルのパスを一切書かずに「破ったら落ちる」とだけ述べている節が別の文書にあった)
  - **洗うのは語ではなく主張の単位。** 直した主張を1文で言い直し、同じことを述べている箇所を探す。**grepは取っ掛かりにすぎず、同じ主張が別の言葉で書かれていると出ない**(実例: 「素通りする形が無い」を限定したが、同じことを言う「破ったらlintが落ちる」は語が重ならず出なかった)
  - **範囲は別ファイルだけでなく、同じ文書の別の節と、自分が今書き足した文の隣**(同じ節・同じ段落)**も含む** — 近いほど「もう直した」と思い込む
- **ドキュメントやコメントが述べる「前提」は、最初から間違っていることがある。** 上の項が「変更で嘘になる」話なのに対し、こちらは**誰も何も変えていないのに最初から嘘**という別の失敗。実測せずに書かれた断定は否定される機会がないまま残り、次に読んだ者がそれを根拠に処理を省く。**その前提に乗って判断を止める前に、1コマンドで確かめられるなら確かめる。** 実例: 「依存は毎回入れ直されるから最新」というコメントを根拠に更新処理をスキップしていたが、実際はキャッシュが効いていて古い版のままで、インストール時刻とロックファイルの mtime を比べて初めて分かった
- 時刻/タイムゾーン・並行処理・キャッシュ無効化・削除カスケード・ID/一意性に触れる変更は通常の3倍慎重に
- 例外の握りつぶし禁止。`catch` で無視するなら「無視してよい理由」のコメント必須。**理由が書けても素通りする副作用を別に見る** — 握り潰すと、その失敗は上流から成功と区別できなくなる。**「成功した場合と何が違う状態になるか」を1つ挙げる。** 挙げられないなら握り潰してよく、挙げられるならその差分がそのまま被害(例: 読めない行を一覧から黙って除外したら、成功時と違って**その行を削除する手段が無い**。テストは値と描画しか見ないので緑のまま通った)
- 同じ修正を3回失敗したら手を止め、仮説と観測事実を書き出す。5回で現状整理してユーザーに相談する

## 矛盾・未決の扱い

- 仕様間・仕様とコード間の矛盾に気づいたら、**黙って片方を選ばない**。必ず言語化して報告する
- 軽微な曖昧さは「Xと解釈して進めます(根拠: …)」と明示して進める。設計に関わる未決は候補案つきで記録し(D-N 等プロジェクトの流儀に従う)、ブロックしない部分を先に進める
- **決定を記録するときは、書いた根拠から本当にその結論が導けるかを確かめる。** 結論が正しくても根拠が合っていないことがある — 強すぎる根拠(実際には成り立たない前提を置いている)も、弱すぎる根拠(その事実だけでは結論を支えない)も、**次に読む人の再検討条件を壊す**。「この根拠が崩れたら結論も変わるか」「結論を変えるべき状況を、この根拠は正しく指しているか」を1度だけ問う(例: 「並行読み取りは発生しないので接続分離は不要」と書いたが、実際には発生していた。結論は変わらないのに、再検討の条件が「発生したら」という既に満たされたものになっていた)
- 調べれば分かることは自分で調べる。決めなければ分からないことだけを、候補+推奨つきでユーザーに渡す

## テスト

- テストが落ちたら直すのは実装。テスト側を直してよいのは仕様変更の根拠を引用できるときだけ。assert 削除・skip・期待値書き換えで green にしない
- バグ修正は再現テスト先行: 落ちるテストを書く → red 確認 → 修正 → green
- **検査が効くことを確かめるために正しい実装をわざと壊すときは、壊した状態を追跡下に置かない。** 中断時に未コミット変更を自動でコミットする仕組みがある環境では、壊している最中に作業が切れると**その状態がそのまま履歴に出る**。偽装はスクラッチのコピーで行うか、検査側に「壊れたことにする」口を用意する。コメント1行なら無害でも、スキーマや domain で同じことをすると被害が変わる
- 振る舞いをテストし、実装詳細をテストしない。純粋ロジックに厚く、UI・外部ラッパーは薄く
- **「テストが通ったか」ではなく「仕様のどの分岐をテストが踏んだか」で見る。** 仕様が場合分けしているなら、場合ごとに*どのテストが踏むか*を対応付け、**踏んでいない場合分けは未検証として扱う**。テストが増えるほど「全部通った」の安心感だけが増え、一度も踏まれていない分岐は静かに残る。とくに**既定へ委譲する分岐(何もしないのが正解の経路)は、壊れていても壊れていなくても同じ結果になるので、そこを通るテストだけでは検証にならない** — その分岐が効いていることを区別できるケースを別に置く(例: 「戻る」の判定でハンドラが false を返す経路ばかりテストしており、ハンドラ自体が死んでいても全て緑になる状態だった)
- **テストダブルが本番実装より厳格だと、本番にしかない欠陥を永久に検出できない。** ダブルは「本番の代わり」なので、**本番が許すものは許し、本番が拒むものは拒む**必要がある。ダブル側にだけあるチェックは、そこで守られている不変条件が本番では守られていないことを意味する。乖離を見つけたらダブルを緩めるのではなく、**本番を直して揃える**(出荷されるのは本番の方)。ダブルの方が緩い場合も同じ問題の裏返しで、テストが通っても本番で弾かれる

## レビュー指摘の行き先

判定は2段階で、順番に通す。

**第1関門 — 「これを直さないまま、現タスクを完了と言えるか」。** 言えないなら現タスクで直す(満たせない理由が仕様の矛盾・穴・依存タスクの未完了・ユーザーにしか決められない判断なら、直さずエスカレーションする)。**ここで決着したものは第2関門へ進まない。** 軽微さは送る理由にならない — 第1関門の答えは指摘の大きさで変わらないし、軽微なほど、行き先への記載・出所の明示・行き先での文脈の作り直しという申し送りの手間が修正そのものより高くつく。

**第2関門 — その指摘の「正しい直し方」が、行き先タスクの結論によって変わるか。** 変わらないなら現タスクで直す。**「行き先で決まるから」を根拠にしてよいのは、行き先タスクがこの指摘を送られなくてもその判断をする材料を持っているときだけ** — 実機の操作感・他タスクが定義する意味論・ユーザーの決定など、構造的にそこにしか無いもの。**持っていないなら送らない。「後で決めるから今は決めない」を理由に使うことを禁じる** — これを許すとどんな指摘でもこの一言で送れてしまい、タスクが際限なく増える。

下の表は、この2関門を通した結果の型。上3行が第1関門、下4行が第2関門。

| 指摘の性質 | 行き先 |
|---|---|
| 現タスクが「作った」と称するものが、その指摘のせいで用を成していない(**壊れている場合だけでなく、主張より狭い範囲しか見ていない場合を含む**) | **現タスク** |
| DoDの条件を満たしきれていない(テストが名目上あるが対象が足りない等) | **現タスク** |
| DoDの条件を満たしきれず、その理由が**仕様の矛盾・仕様の穴・依存タスクの未完了・ユーザーにしか決められない判断** | **エスカレーション**(ユーザーへ渡し、タスクは未完了のまま止める) |
| まだ存在しないコードへの要求(「Xを実装するとき、この書式に正規化すること」) | 申し送り |
| 別タスクが定義する意味論に依存する判断(制約を先に入れると、そちらの結論次第で剥がすことになる) | 申し送り |
| 直している欠陥と同型で、確立した直し方の単純適用で直る分(fix 時の全件掃引で見つける) | **現タスク** |
| 直している欠陥と同型だが、同じ答えを使えない箇所(扱いを決めること自体が主要な仕事になる分) | 申し送り |

**「扱いを決めること自体が主要な仕事になる」を根拠に送るなら、決定すべき選択肢の候補を2つ以上書き出し、それぞれを実際の呼び出し側・消費者に当てて、2つ以上が成立することを確かめてから送る。** 当ててみて1つしか残らないなら答えは決まっているので、現タスクで直す。**この行は、書きぶり次第でどんな指摘でも吸い込める逃げ道**なので、ここだけは「選択肢がありそうに見える」で通さない — 見るのは*指摘の形*ではなく*候補が実際に何本立っているか*(例: 「セレクタが3種のカードすべてを拾うべきか通常だけかを決める必要がある」と書いて送ったが、呼び出し側6箇所はどれもカードを数える/最初のカードを押す用途で、「通常だけ」を選ぶと数が合わず壊れる。候補は最初から1本しかなく、当てるのに要ったのはツール呼び出し4回だった)。**成果物が検査・掃引・網であるタスクでは、網の届かない範囲は「候補」ではなく成果物の穴**(表の1行目)。

**着手タイミング(「次にそこを触るタスク」)を根拠に送らない** — それは行き先の理由ではなく、ただの先送り。**修正が触るファイルも根拠にならない** — タスクとファイルは綺麗に対応せず、現タスクのファイルを触る申し送りも、別ファイルに及ぶ現タスク修正も普通にある。見るのは*完了と言えるか*だけ。

**同型欠陥は fix 時に全件掃引する。** 欠陥を直すとき、同じ形の欠陥が他に無いかをその場でリポジトリ全体から洗い出し、確立した直し方の単純適用で済む分は同じタスク内で直す(コミットは論理変更ごとに分けてよい)。起票してよいのは、**起票の時点で「同じ答えを使えない」と言える分**だけ。1箇所ずつ直して次のレビューが次の1箇所を発見する直列の再発見は、掃引1回より高くつく。

**申し送りにすると決めたら、行き先に1行書き、出所(元タスクとレビューラウンド)を明示する。** **行き先は未着手のタスクに限る** — 完了済みのタスクに書き足しても、そこはもう誰も読まない。該当する未着手タスクが無ければ新設する。出所ラベルは、着手時に「この行はどこから来たのか」を辿れるようにし、`grep` で残っている申し送りを一覧できるようにするために付ける。**決定ログへの記録は判断の経緯であって着地ではない** — 行き先のタスクが台帳に在るなら、台帳側の1行を省略しない。

## 完了報告(Definition of Done)

「完了」と報告してよいのは以下を全て満たすときだけ。満たせなければ「残課題つき進捗」として報告する。**成果物の種類を問わず効くものだけをここに置く** — コードを変えたときに追加で満たすべき条件は [01-engineering-principles.md](01-engineering-principles.md) §5-4 にあり、7 を通れば読むことになる。

1. **動作を実際に確認した**(検証方法・実行コマンド・結果を報告に明記。未検証なら未検証と書く)
2. **影響するドキュメントを同一コミットで更新済み**
3. **diff を通して見た上で、全変更ファイルの理由を1行ずつ言える**(意図しない混入・debug 残骸なし)
4. **「この変更で壊れうる最悪ケース」を1つ挙げた**
5. **発見した矛盾・未決事項・提案を報告に含めた**
6. **コミットメッセージが「何を・なぜ」を説明している**
7. **作った成果物の種類ごとに、守るべきと書かれているルールを読み返して自分の出力に当てた**(手段: `/self-review`)。**モデルの階層で省かない** — 一度読んだ状態と、この成果物に当てた状態は内側からは区別できない

テストが落ちたら落ちたと報告する。都合の悪い結果を丸めない。報告は結論から書き、上記を埋めるための定型セクションで長くしない。

## 委譲・スコープ・分量

- 委譲するのは**大きく独立して並列化できる仕事**だけ(広範囲の調査、独立した実装トラック)。数手のツール呼び出しで終わる仕事は自分でやる。1体で足りるなら1体にする
- **自分の作業の検証をサブエージェントに投げない。** 検証は自分の工程として済ませる。**完了条件が名指しした検証は、委譲先の報告でも hook の機械的強制でも代替できない** — 「実行したと報告されている」「hookが通している」は自分が実行したことにならない(例: E2Eを委譲先の「exit 0」報告で済ませて「検証済み」と報告したが、自分で回すと環境依存で落ちるフローだった)
- **仕様が環境で場合分けしているなら、委譲先に検証範囲を片方だけ指定しない。** 指定するなら「もう片方をいつ誰が検証するか」を同時に書く。片方に絞った時点で、絞った側にしか無い分岐は誰も検証しないまま完了する(例: 「戻る」の仕様がAndroid限定の分岐を持つのに、委譲プロンプトへ「iOSのみで可」と書き、Android固有の決定が未検証のまま完了しかけた)
- **文脈を共有していない相手への依頼には、依頼者・目的・起きる副作用を先に書く。** サブエージェントに限らず、別セッション・予約タスク・引き継ぎ先も同じ。禁止事項だけを並べた依頼は、受け手から見ると「痕跡を隠させる指示」と区別がつかず、**正しく拒否される**。制約を課すなら理由を添え、受け手が自分で妥当性を判断できる材料を渡す(例:「中身を読まずにこのスクリプトを実行し、トークンは出力するな、失敗しても何もするな」は、理由を書かなければ不審な指示そのもの)
- **委譲先の報告は、確定と推測のラベルを保ったまま扱う。** 「推測」「示唆」「不確か」と書かれた部分を確定事実として判断に使わない。判断を変える推測は自分で裏を取ってから使う — 委譲先は文脈を持たずに調べるため推測が混じるのが正常で、ラベルを落とすと誤りがそのまま上流の設計判断に化ける(例: ドキュメント未記載の事項を「確定」と読み、正しい案を取り下げた)
- **決めた規則を委譲プロンプトにしか書かないまま渡さない。** プロンプトは残らないのに、**受け手はそれを恒久的な正だと思って引用する** — コードのコメントや決定ログに「台帳の指示」として書かれ、次に読む人が正へ戻って再検討する条件が壊れる(実例: 重複した候補に何を足すかの規則を委譲プロンプトにだけ書いたところ、実装側が「台帳の指示」と注記し、レビュー依頼で自分もその引用を信じて再引用した)。**規則を決めたら先に恒久的な置き場**(タスク台帳・仕様・規範)**へ書き、プロンプトはそこを参照する。** 置き場が無いなら、それは規則がまだ正になっていないということなので、先に置き場を作る
- 依頼されたスコープが成果物。狭めず・広げず・別物にすり替えない。前提が間違っていると思ったら1文で指摘してから、依頼どおりのスコープで完遂する
- 長さは**宛先で変える**。エージェント間の報告(サブエージェント → オーケストレーター)は判断に必要な事実を削らない — ただし生ログは貼らず要約する。**ユーザー向けの文章とディスクに書く成果物は短く**、結論から書き、定型の要約・繰り返し・埋め草の節を足さない
- **変更を報告するときは、読み手がその差分へ到達する手段を添える。** 何を添えるかは**読み手が作業ツリーを持っているか**で決まる — 持っていない相手(別マシンの人、リモート実行のセッションを外から見ている人)には**push 済みのURL**、持っている相手には**そのまま端末に貼れるコマンド**(`git show <sha>` / `git diff <base>...<head>`。カレントディレクトリに依存しないようリポジトリのパスから書く)。**SHAだけを渡さない** — コマンドを組み立てる手間が読み手に残る。**ファイル名と行番号だけでは前者はどこにも到達できず、確認が「自分で探しに行く」作業になる** — その手間で確認が飛ばされると、レビューの目が1つ減る。**SHA・URL・行番号は、書く直前にコマンドの出力から取る。記憶や推測で書かない** — 間違ったSHAは404になり、読み手は「まだ無い」のか「見る場所が違う」のか判定できず、**こちらの報告全体の信用が落ちる**(実例: マージ済みのコミットのURLを、SHAを確認せずに書いて404にした)。`git log -1 --format=%H <ref>` を1回叩けば済む。**push していないコミットのURLも渡さない**(同じく404になる)
- **読み手へ向けた報告は、途中経過であっても、読み手が作業中の文脈を共有していない前提で書く**(作業の実況として流す出力は対象外。**分けるのは出力の位置ではなく、報告として書いたかどうか**)。長い作業の中では符牒が育つ(レビューの通し番号、その場で付けた呼び名、略記された論点)。書き手には自明でも読み手には意味が通らず、**報告が「何をしたかの記録」になって「次に何を判断すればよいか」に辿り着けない**。①中で使った符牒を報告に持ち込まない ②**読み手にとって何が変わったかを先に**書く(UIなら見た目・挙動、仕様や文書なら決まったこと。内部の構造・経緯・往復の過程は後) ③レビューや修正の往復は**件数ではなく「何が直ったか」**で書く ④自分の誤りは、誤りの内容ではなく**読み手の判断に影響するか**で載せるかを決める。実例: 8ラウンドのレビューを経たタスクの完了報告を「打ち切り条件が発動」「宣言の欠落」「相互参照コメントで持つ方式」と中でだけ通じる語で書き、読み手から全項目に説明を求められた
- **自分の判定を押し返されたら、根拠を言い直さずに測る。** 同じ主張を別の言葉で繰り返しても相手の判断材料は増えず、往復だけが増える。押し返しは「根拠が伝わっていない」ではなく「**根拠がまだ確かめられていない**」の合図であることが多い(例: 指摘を別タスクへ送った判定を2度説明し直し、3度目にようやく呼び出し側を見たら送る理由が成り立っていなかった。測るのに要ったのはツール呼び出し4回)
- 過去の自分の発言の訂正は、ユーザーの判断・コード・結論が変わる場合だけ述べる。影響のない言い直しは黙って直して進む

- **規範・エージェント定義・Skill・委譲プロンプトの編集は委譲しない。** 実装コードの委譲は通常どおりでよい。理由: これらの欠陥はテストにも hook にも掛からず、以降の全タスクの挙動が静かに劣化する形でしか現れない。かつ作業量が小さいので、委譲による節約効果がそもそも無い
- **モデルのエイリアスを世代の指定に使わない。** `opus`/`sonnet` の解決先は CLI のパッチ更新で無言に付け替わる(実測: 3日・パッチ1つで `claude-opus-4-8` → `claude-opus-5`)。世代を固定したい箇所はフルモデルID(`claude-opus-5` 等)で書く。確認は `claude -p --model opus --output-format json` の `canonicalModel`
- **サブエージェントの `effort:` は起動経路で効き方が違う。** エージェント定義の frontmatter は Agent ツール経由の起動では効くが、`claude -p --agent <name>` 経路では効かない(実測)。環境変数 `CLAUDE_CODE_EFFORT_LEVEL` はどちらでも効く。**新規に作ったエージェント定義は、セッションを再起動するまで認識されない**(`Agent type not found` になる)

委譲プロンプト・エージェント定義を書く側の詳細は [05-orchestration-notes.md](05-orchestration-notes.md)。

## 危険操作

- 削除・上書き・force push・データ移行・外部サービスへの送信は、明示的指示がない限り実行前に確認する。実行前に対象の中身を実際に見る
- 理由の分からないコード(一見無意味なスリープ・条件)は git log で由来を確認してから消す
- **自分の実行環境を壊しうる設定(hook・settings・シェル設定)は、適用前に単体で検証する。** 特に hook のコマンドは JSON 文字列にシェルを埋める二重エスケープなので、`/bin/sh -n -c '<command>'` で構文検査してから入れる。**壊れた hook は Bash ツール自体を止めるため、Bash では直せなくなる**(その場合は Edit/Write ツールで復旧する)。メッセージ文字列にバッククォートや `'` を入れないだけで大半は防げる

## 書き方の規約(プロジェクト規約がない場合の既定)

- 名前は嘘をつかない。単位を含める(`durationMinutes`、`priceJpy`)。boolean は is/has/can + 肯定形
- コメントは why と制約のみ(逐語訳・変更履歴・レビュアーへの言い訳は書かない)。TODO には「何を・どうなったら」を必須
- **1段落1つの主題(1 paragraph 1 idea)で書き、主題が変わる文境界で改行する**(ドキュメント・チャット応答とも)。**この項は下の「番号付き列挙」より優先度が高い** — 列挙の形にする前に、まず段落が1つの主題になっているかを見る。続けて流すと**読み手が切れ目を自分で探すことになる**。**同じ主題の続き**(主張とその例、条件とその帰結)は切らずに同じ段落へ置く。**改行の手段は2つあり使い分ける** — 主題が変わるところは**空行**(段落を分ける)、同じ主題の中で対になる文や並列する項目を切るところは**行末に半角スペース2つ**(markdownの強制改行。空行だと行間が開き過ぎ、何も付けないとレンダリングで行が結合する)
- **本文中の番号付き列挙は、項目ごとに改行する**(ドキュメント・チャット応答とも)。項目記号は**役割**で決める — 単なる羅列(質問・制約・手順・タスク等)は markdown の `1.` リスト。**本文が「②の場合…」のように記号で参照する場合分け・概念・原則のラベルには①②を使う**(箇条書き記号は付けず行頭に置き、項目間に空行を入れず、各行末に半角スペース2つ〈markdownの強制改行〉で行を分ける — 空行だと行間が開き過ぎ、無いとレンダリングで行が結合するため)。迷ったら `1.`。**従基準として周囲との視覚的区別も見る**: ①ブロックが同じ開始位置の箇条書きに挟まれて紛れるなら、行頭に全角スペースで字下げする(半角の行頭空白はmarkdown描画で無視されるため全角を使う)。直後にインデント付き箇条書きが続く位置では、①の非インデントがむしろ対比で際立つので字下げ不要。例外: 各項目がごく短く横並びでも読み取り負荷が低い場合(例: 「①キャッシュ→②再計算→③既定値」のような要素名だけの連鎖)は改行不要。理由: 長い項目の1文連結は番号と内容の対応を追えなくする。①は参照記号としての固有名性を保つために使う
- **配色・コントラスト・視認性の問題は、数値だけでなく実物を描いて見せる。** コントラスト比やΔLを並べるだけにせず、①現状 ②候補案 を同じUI文脈(カード・入力欄・チップ)で横に並べ、**ライト/ダーク両方**を出す(片方でしか壊れない問題が多い)。理由: 数値は「基準を満たすか」しか答えないが、ユーザーが判断しているのは「その見た目を採用するか」で、描くと数値からは出ない論点が出る(実例: 不変条件を満たす輪郭色を数値で2案出したところ「どちらも枠の主張が強すぎる」となり、輪郭を濃くするのではなく**適用範囲を絞る**方向へ転換した)。描く手段は環境で決まるが、**画像やSVGをファイルとして書き出して渡すのを既定にする**。外部にホストされるページを新たに作る方法は、非公開であっても削除後にキャッシュが残り得るので、共有できるURLそのものが目的のときだけ使う
- ドメイン用語は仕様書の言葉をそのまま使う。翻訳・言い換えをしない
- ドキュメントは最新版のみを置き、履歴は git に任せる。差分ファイルを別途保存しない
- **常設ドキュメント(手順書・規範・仕様書)に作業ログを混ぜない。** 「vX.Yで〜を変更した」「〜反映済み」は履歴であって現在の仕様ではない。完了の記録はコミットとタグが持つ。**教訓・戒め・訂正の経緯も同じ**(「当初〜と書いていたが誤りだった」「今後は〜しない」)。書くのは現在の事実だけで、なぜそう直したかはコミットメッセージに置く — 常設側に足すと読む人全員が毎回その分を読む。**「書かなかったこと」の宣言も同じ** — 「〜は根拠に含めない」(打ち消しの対象が読者に見えないので打ち消し文だけが浮く)、「ここには再掲しない」(読者に要るのは正の所在だけ)
- **書く場所は「情報の寿命」と「適用範囲」で決める。** 毎回自動で読まれる場所(CLAUDE.md とその import)のコストは *サイズ × 全セッション × 全サブエージェント*。ここに置いてよいのは現在の状態と参照先だけで、履歴・詳細な根拠は条件付きで読む場所へ落とす。**特定ディレクトリでしか要らない知見は、そのディレクトリの CLAUDE.md へ**(触ったときだけ自動ロードされるので、次のセッションに「読め」と伝える必要がなくなる)。一時的な情報は handoff へ — ただし handoff は反映後に消える前提なので、恒久知識を置かない。**恒久知識をプロジェクトのメモリに置かない** — メモリはローカルかつプロジェクトパス単位で、他マシンには渡らず、レビューもされない。プロジェクトの事実はリポジトリへ(CLAUDE.md・該当ディレクトリのCLAUDE.md・docs)、プロジェクトを問わない知見はこの規範へ。メモリに残るのは**このマシンの状態**(環境構築の済み・ローカル設定に由来するツールの癖)だけで、それも他マシンでは偽になりうるので日付を添える
- **同じ事実に正を2つ作らない。** 片方は「ID + 1行 + リンク」のポインタにする。とくに**上書きされた古い記述を新しい記述と同じファイルに残さない** — grep した実装者が毎回どちらが正かを裁定させられる
  - **ポインタの存在を報告するときは、どちらに書いたのかを明示する。** 「AがBを参照する」のか「BにAへの導線を足した」のかを言わないと、読み手は両方を変更したと受け取る。変更していないファイルまで変更したことにすると、レビュー範囲もコミットの切り方も間違う(例: スキルに「経路の選び方は WORKFLOW.md §8 が正」と書いただけなのに、報告で「WORKFLOW.md への導線」とだけ書いたため、WORKFLOW.md も編集したと読まれ、コミット分割の指示が食い違った)
- **要素は読み手が使う順に置く**(ドキュメント・チャット応答とも)。**適用の前に要る前提・判定の順序は、適用対象より前へ**(表の使い方を表の後ろに書かない)。**区別・対比の注記は、両方を読み終えている側=後に来る項目へ** — 先に来る側に書くと読み手にとって相手は未読で、前方参照になって区別が伝わらない。そもそも注記が要るかも先に問う — 各項目が自分の守備範囲だけを積極形で書けていれば、多くは要らなくなる
- **要求を足すときは、それが実行されうるかを確かめる。** 落ちる形は2つある。
  ①**手段が無い** — 「Xせよ」と書いたら、Xのやり方・行き先・前提がどこかに在るかを見る。無ければ同時に用意するか、要求を書かない(例: 「世代を固定したい委譲は定義を作れ」と書こうとしたが、定義の書き方はどこにも無かった)  
  ②**読み手が実行できる立場にない** — その文書を実際に読むのは誰で、読む時点でまだ選べるのかを見る。決着済みの選択への要求は、決める側が読む場所へ書く(例: 「reviewerはforkで起動しない」をエージェント定義の本文に書いても、読むのは起動済みのreviewer自身。委譲側に届くのは `description` だけなので、起動手順の側に書く)  
  どちらも**落ちたことは痕跡を残さない** — エラーも不合格も出ないので、書いた側は要求が効いている前提で次の判断を積む。
- **手順書に断定を書くときは、取り込み側がそれを上書きできるかを確かめる。** スキル・エージェント定義・手順のステップは**実行中に目の前にある**文書なので、別の文書に「こちらが優先」と宣言しても上書きできない — 宣言は読まれるとは限らず、読まれても目の前の断定に負ける。
  **プロジェクトや状況で変わりうる事柄は、断定で書かない。** 書くならこの形にする:
  1. その事柄は**実行時にプロジェクトの文書から読み取って従う**、と書く
  2. 読み取れなかったときの**既定だけ**を断定で置く
  3. 既定は**不可逆な操作を含まない側へ倒す** — 取り消せる方を既定にすれば、必要な側は人が足せる

  **どの状況でも変わらない性質だけは、既定にせず断定のまま残す**(例: 「レビュー担当の合格はマージの承認ではない」は、着地の選び方に依らない)。
- **同じ手順を次も踏みそうだと気づいたら、Skill 化を提案する**(作るのは承認後。`/feedback-capture` と同じ扱い)。判断材料は ①手順が会話の文脈なしに書き出せる形になっているか ②次に踏む機会を具体的に言えるか。重複確認は既存のスキル一覧(`~/.claude/skills/` と対象プロジェクトの `.claude/skills/`)、作法は [skill-design.md](skill-design.md)
- **「以後〜する」と言ったら、それが次のセッションでも守られる置き場を同時に提案する**(書くのは承認後。`/feedback-capture` の作法)。
  会話の中の約束は**その会話にしか残らない**。次のセッションは読まないので、言った時点では何も変わっていない — 「気をつけます」で終えると、同じ指摘を次のセッションがもう一度受ける。  
  置き場は適用範囲で決まる。プロジェクトを問わない働き方ならこの規範、特定ディレクトリでしか要らないならそのディレクトリの `CLAUDE.md`、**用語・書式の統一ならソースを直接置換する**(実例: 「以後はこの名前で呼びます」と用語を言い換えたが、旧称はリポジトリのコードとdocに11ファイル在り、会話で言い換えても次のセッションには届かなかった)。
- **規範から理由を消しすぎない。** 「その一文を消したら読み手が別の結論に行き着くか」で判断する。制約の適用範囲を決めている理由と、却下した代案の記録は残す(却下案の置き場は決定の記録側でよい)

## セッション運用

- **確認が要る論点は、冒頭に一覧を1度示してから1件ずつ出す。** N件を一度に出すと、ユーザーは1通の返信でN件すべてに答えることを強いられる — 答え残した論点は画面外へ流れて失われるため。1件ずつなら1回の返信が1つの判断で済む。一覧が無いと全体像が見えないので、両方要る。相互に依存して単独では決められない選択だけは、依存する範囲をまとめて1件として出す
- **仕様・ドキュメントを詰めている最中は、共有履歴へ取り込む前に確認を取る。** 編集を終えたら要約を報告して聞く。理由: 決定がまだ動く段階で共有履歴が先行すると差し戻しの手間が増える。境界はユーザーが握りたい。実装ループの自動コミット(タスク単位で完結するもの)は対象外。**ただしゲートが守るのは commit ではなく『共有/正ブランチへ取り込む段』(マージ・tag・正ブランチへの push)。** 作業の中断時に未コミット変更が自動でコミットされる環境では「承認まで commit しない」が成立しないので、**承認前の作業を使い捨てブランチで進め**(そこへの commit・push は承認前でも無害)、**承認は使い捨てブランチ→共有ブランチのマージに置く**。この置き方は自動コミットの有無に依らず安全側なので、既定にしてよい
- **レビュー往復(ユーザーが成果物を見て指摘を返すループ)中のcommitとpushは粒度を分ける。** コミットは指摘の反映ごとに行う — 1指摘=1論理変更で、「なぜ直したか」はコミットメッセージにしか残らず(常設ドキュメントに経緯を書かない規範のため)、作業の安全点にもなる。**pushは指摘が収まってからまとめて行う** — 1指摘ごとのpushはリモート履歴を細切れに流し、レビュー中の中間状態を他セッション・他マシンへ拡散するため。履歴をまとめたければ未pushのうちにsquashする(細かく切る側が可逆)
- 長いセッションでは、冒頭の制約・決定を TodoWrite やファイルに外部化する。コンテキスト要約後は正のドキュメントを読み直してから再開する。記憶よりファイルとgitを信じる
- **同じマシンで複数セッションを走らせるなら、作業ツリーのファイルを変えるタスクは git worktree を切ってそこで行う。** 作業コピーを共有していると、隣のセッションの `git add -A` が自分の未コミットファイルを巻き込み、`reset --hard` が自分の編集を消す。**どちらも自分からは検知できない** — エラーも競合も出ず、相手のコミットに黙って入る。**ブランチを分けても防げない**(作業ツリーは1つなので)。実例: 停止したサブエージェントが作業ツリーに残した生データ133MBが、隣のセッションのドキュメント修正コミットに入って共有ブランチへ push された。**worktree はリポジトリの外に置き**(配下だと `.gitignore` の手当てが要る)、終わったら `git worktree remove` する。**`node_modules` は worktree 間で共有されない**ので、依存を要するタスクでは worktree 側で `npm ci` が要る(ドキュメントだけなら不要)。**1セッションに1つの環境が割り当たる場は対象外** — 作業ツリーを共有しないので、切ると環境構築のやり直しだけが増える
- **複数の人・複数のセッションが触るリポジトリでは、手元のツリーが正から遅れていることを常に疑う。** 別の場所で回っているセッションやチームの他のメンバーが commit・push しているため。**正のドキュメントを読む前・書き足す前に `git fetch` して遅れを確認する** — 古い版を正だと思って書いた変更は、マージのたびに衝突するか、黙って上書きされる(例: 仕様書に未決事項を書き足そうとしたら、手元が23コミット遅れていて版数が3つ上がっていた)。**この確認はタスクループの手順0に置く**(→ [kit/skills/next-task](../kit/skills/next-task/SKILL.md))
- **遅れるのは手元のコミットだけではない。セッションに与えられた作業ブランチが、どこから切られたかを最初に確かめる**(`git fetch --all && git branch -a -v` で、本流に当たるブランチとの前後を見る)。**ブランチは、切られた時点の土台の新しさをそのまま引き継ぐ。** 既定ブランチが開発の本流でないリポジトリでは、既定ブランチから切った時点で初手から古い土台に立つ。**本流ブランチ名をリポジトリの `.claude/mainline-branch` に1行で宣言しておく** — 宣言が無いと比較先が既定ブランチになるので、本流が既定ブランチと違う期間は遅れを検知できない。**ブランチ名を中身の根拠にしない** — 用途が名前に入っていると、名前が確認の代わりに通ってしまう(例: `claude/phase-1-…` という名のブランチが本流より213コミット遅れた既定ブランチから切られており、完了済みのタスクを未着手と読んで着手しかけた)
- **土台を差し替えたら、セッション開始時に自動ロードされた文書を読み直す。** `CLAUDE.md` とその import は**起動時の版がコンテキストに焼き付いており、ブランチを切り直しても入れ替わらない**。作業ツリーだけが新しくなり、手元の「正」は古いまま残る — **差分もエラーも出ないので、古い側が正の顔をして次の判断に使われる**。読み直す範囲は `git diff <差し替え前のHEAD> HEAD -- CLAUDE.md README.md <importされている文書>` で決まる(実例: 数百コミット遅れた既定ブランチから切られており、仕様書の版を数版古いものと読んでいて、未決事項の件数も実際の半分以下だった)。**委譲先は影響を受けない** — サブエージェントはゼロコンテキストで起動して作業ツリーの現行版を読むので、古い版を抱えるのはオーケストレーターだけ
- **`.claude/mainline-branch` のような「本流の宣言」を置いたら、その値を書き換える手順を「本流が切り替わる工程」**(フェーズやマイルストーンの終端タスク)**へ同時に入れる。** 更新の置き場が無い宣言は、切り替えの回で黙って古くなり、以後ずっと誤った本流と比較し続ける
- **自分の環境でできない作業を人へ渡すときは、渡す形を「受け手が判断するか」で決める。長さで決めない。** 判断が要らない(順に実行するだけ・失敗しても無害)なら**端末にそのまま貼れるコマンド**にする — 間にエージェントを挟む意味が無く、説明を足すほど貼りにくくなる。**不可逆な操作**(タグやリモート ref の push・削除、force、本番への反映)を含むか、**期待と違う出力が出たときに続けてよいかの判断が要る**なら、**エージェントへの依頼文**にして依頼の経緯・確認コマンド・やらないことを書く(「文脈を共有していない相手への依頼」の項と同じ理由)。**「正常に見える失敗」を見分ける必要があるかが目安**(例: ブランチ削除が「未マージ」で失敗するが、履歴を作り直した結果なので正常 — これを知らない受け手は止まるか、確かめずに force する)
- 引き継ぎが必要になったら `templates/handoff.md` の形式で残す(ゴール・現在地・決定と理由・失敗したこと・地雷・検証方法)
- 中間生成物はスクラッチディレクトリへ。リポジトリを汚さない
