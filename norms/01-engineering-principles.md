## 1. 設計思想(常に意識していること)

### 1-1. 状態を減らすことが最強の品質施策
- 導出できる値は保存しない(例: 明細の合計は保存せず明細から導出し、編集不可にする)。保存した瞬間に「不整合」という新しいバグクラスが生まれる。
- 不正な状態を「バリデーションで弾く」より「型・構造上作れなくする」を優先する。
- 「未定」「不明」のような特別状態を追加する前に、その状態自体を廃止できないか考える。特別状態は全分岐に if を増やし続ける。

### 1-2. 複雑さの置き場所を選ぶ
複雑さは消せないが、置き場所は選べる。優先順位: **内部のルールベースロジック > 型システム > 呼び出し側のコード > UI/ユーザー**。ユーザーにモード切替や設定を露出させるのは最終手段。内部で吸収できる複雑さをUIに出したら設計の負け。

### 1-3. 抽象は差し替え点にだけ入れる
- 実際に差し替える具体的な予定がある箇所(例: 通知チャネル、オブジェクトストレージ)にはプロバイダ非依存の抽象を入れ、設定変更だけで差し替えが完結するようにする。
- それ以外の場所に「将来のため」の抽象を入れない。投機的な抽象は将来の要件を当てられず、読み手のコストだけが残る。3回同じパターンが出てから抽象化する。
- 抽象化するのは「判断・推論」の層。ツール・データ供給層(検索、外部API接続)とは別物として分離する。代替関係と補完関係を混同しない。

### 1-4. 決定の可逆性で慎重さを変える
- 可逆な決定(変数名、内部実装、ローカルの構成)は素早く決めて進む。
- 不可逆・高コストな決定(保存データ形式、公開API、外部サービス契約、ライブラリの深い結合)は候補比較を書き、必要なら未決事項として保留する。
- 「保留」は立派な決定。判断材料が揃っていないのに決めるより、番号を付けて管理し前進する方が速い。

### 1-5. 単一ソース原則
同じ情報を2箇所に書かない。書かざるを得ないときは「正はどちらか」を明記する。ドキュメントは常に最新版のみを置き、履歴は git に任せる(版数付きファイルの複製を作らない)。

### 1-6. 統制は「非対称の根拠」と「失うもの」で判断する
- **非対称な制約を設けるなら、非対称性の根拠を言えること。** 「こちらは危険だから禁じる」と言うなら、もう片方が安全な理由を示せなければならない。示せないなら、制約が間違っているか、対称に掛けるべきかのどちらか。
- **統制は必ず何かを失わせる。** 足す前に「これで失うもの」を1つ挙げる。守るものより失うものが大きいなら掛けない。
- 例: CI からのデプロイは許可したまま、手元からのデプロイを禁じた。だが手元も同じ資格情報で同じ手順を踏むので脅威モデルに差がなく、代償として障害時に最も速い復旧経路を失っていた。

### 1-7. 情報を外に出す機能では「告知」と「自動取得の遮断」を別々に設計する
公開・共有・エクスポート・外部送信を作るときは、次の2つを**別の対策として**洗う。片方でもう片方は代替できない。

- **① ユーザーへの告知** — 何が誰に見えるかを、**操作の直前に**示す。これが守るのは「ユーザーが自分で渡す相手」の範囲。
- **② 意図しない自動取得の遮断** — クローラ、URLプレビュー生成ボット、キャッシュ、リファラなど、**ユーザーが誰にも渡していないのに機械が取りに来る経路**を塞ぐ。①がどれだけ丁寧でも、これは1つも防げない。

**②を見落としやすいのは、経路がユーザーの操作として現れないから。** 「リンクを誰に送るか」は目に見えるが、「送った先のサービスが自動でページを取得する」ことは画面に出ない。

典型例が「推測不能なURLを知っている人だけが開けるページ」。①の告知(「URLが転送されれば誰でも開けます」)を入れても、②は別に要る — チャットアプリにURLを貼った時点でプレビュー生成ボットがページを取得し、内容の抜粋が第三者サービスにキャッシュされるため、`noindex` だけでは足りない。塞ぐなら配信ドメインを分けて `robots.txt` を全面 Disallow にし、プレビュー用メタデータに中身を出さない。**なお遵守は相手側に依存するので、確実なのは「URLを知られないこと」だけ** — その限界も仕様に書き、①の告知でユーザーが引き受けられるようにする。

## 2. 実装前に確認すべき事項(チェックリスト)

コードを1行書く前に、以下を確認する。全部で数分の作業であり、省くと数時間の手戻りになる。

1. **正の仕様はどれか** — spec / CLAUDE.md / issue / ユーザー発言。矛盾があれば着手前に解消。
2. **完了条件を1文で言えるか** — 言えなければタスクの理解が足りない。質問するか、自分の解釈を明示して確認を取る。
3. **既存の類似実装を1つ読む** — 同じ種類の処理(画面、API、テスト)が既にあるなら、その規約(命名、エラー処理、ディレクトリ構成)に従う。自分のスタイルを持ち込まない。
4. **影響範囲の grep** — 変更対象のシンボルの全使用箇所。特に: 呼び出し元、テスト、シリアライズ、設定ファイル、ドキュメント内の言及。
5. **そのファイルの git log 直近数件** — 最近の変更理由を知らずに触ると、直したばかりのバグを再導入する。
6. **不可逆操作が含まれるか** — 含まれるなら計画に明記し、必要なら確認を取る。
7. **既存テストの実行** — 着手前に green であることを確認する。着手前から red なら、それは自分の変更のせいではないと確定させておく。

## 3. タスクの進め方

**探索 → 計画 → 実行 → 検証 を分離する。** 混ぜると全部が中途半端になる。

- **探索**: 読むだけ。ここでコードを書き始めない。分かったこと・分からないことをメモ。
- **計画**: 変更するファイル一覧、変更順序、検証方法を先に書く。大きな変更は plan モード・TodoWrite で見える化。計画に「やらないこと」も書く(スコープの外周を明示)。
- **実行**: 計画に沿って小さい単位で。計画とズレ始めたら実行を止めて計画に戻る(ズレたまま進むのが一番高くつく)。
- **検証**: テスト・実行・diff 自己レビュー。検証は実行の「ついで」ではなく独立した工程。

その他:
- 1コミット = 1論理変更。動作変更とリファクタリングを同じコミットに混ぜない。

**「1論理変更」とは、一文で「何を・なぜ」を言い切れて、一部だけ取り消すと意味をなさなくなる変更の最小のまとまり。** 判定は3つの問いで行う。

1. **一文で言えるか** — 「X を Y にした(なぜなら Z)」と言い切れるか。接続詞で「〜と、〜と」と並ぶなら複数
2. **一部だけ戻せるか** — 一部を revert して残りが壊れずに意味をなすなら、**分けられる別の変更**。一部を戻すと壊れるなら1つ
3. **別々に是非を判断できるか** — 「これは入れるがあれは入れない」が成立するなら別

**1つになる例**: バグ修正とその再現テスト(テストだけでは red、修正だけでは直った証拠が無い)。シグネチャ変更と全呼び出し元の追随。同じ答えの単純適用で済む同型欠陥の全件掃引。
**2つに分かれる例**: バグ修正と、ついでの変数名リネーム。機能追加と、その周辺のリファクタリング。
- 大きいタスクは「縦切り」(1ユースケースを型→ロジック→UIまで貫通させる)を優先し、横切り(全画面の型だけ先に全部作る)を避ける。縦切りは早期に統合の問題を露呈させる。
- 作業ログ・中間生成物はスクラッチディレクトリへ。リポジトリを汚さない。

## 4. 実装順序の考え方

1. **契約から固める**: 型定義・データモデル・API シグネチャを最初に書く。契約が固まれば、実装は並列化・委譲できる。
2. **リスクの高い未知を先に潰す**: 「できるかどうか分からないこと」(外部APIの挙動、OSの制約、権限)は最初にスパイクで検証する。できると分かっていることを先にやって、最後に「できませんでした」となるのが最悪の順序。
3. **純粋ロジック → I/O → UI**: 依存の少ない層から。純粋ロジックはテストが書きやすく、ここが固まると上物のバグが激減する。
4. **ハッピーパス → エッジケース → エラー処理**: ただしエラー処理を「あとで」のまま完了にしない(§15 参照)。

## 5. 品質基準

**コンパイル・静的検査・既存テストが green なのは「品質」ではなく「最低ライン」。** 品質と言えるのは、次の3つを満たしたとき。

### 5-1. 必ず確認するケース

- **件数の境界**: 空 / 0件 / 1件 / 最大件数
- **値の境界**: null・undefined、重複、日付の跨ぎ・月末・年末、タイムゾーン、全角・半角・絵文字を含む文字列、極端に長い入力
- **非同期処理**: 順序が保証されない前提で読む。「たまたま順序通りに動いている」コードを検出する。連打・二重送信・**破棄済みの対象への書き込み**
- **表示を持つなら**: 文字数超過時の折返し、日付・数値の書式、入力途中(IME 変換中など)の挙動

### 5-2. 変更耐性(仕様変更に耐えられるか)

**実装した本人が実装中に自己チェックするのが本線で、レビューは見落とし検知のバックストップ。** 網羅ではないので、ここにない観点でも破綻シナリオを示せるなら指摘してよい。

- **分岐の網羅性の欠落**: タグ付きの型(判別可能な union・sealed class・enum など)による分岐で、**その言語で網羅性を強制する手段**(exhaustive check・網羅性検査つきの match など)が使われていない箇所。新しい種別を足したときに**コンパイル/検査で検知できない**構造は重大
- **ロジックのプレゼンテーション層への漏れ**: 仕様に数値・ルールがある処理(既定値の算出・集計式・競合解決の判定など)が、画面・ハンドラ・テンプレートに直接書かれていないか。**テスト可能な純粋関数として分離**する(呼び出し用の薄いラッパを被せるのは可だが、ロジック自体をラッパの中に書かない)
- **数値・文字列の重複**: 仕様由来の定数(閾値・上限・既定値など)が複数箇所にリテラルでコピーされていないか。**1箇所を正として参照する構造**になっているか
- **派生値の独立ハードコード**: 見た目は別々の数値でも、実は同じ基準から算出されるべき従属関係にある値が、それぞれ個別のリテラルとして書かれていないか。**基準値を1つ変えたときに、揃うべき値が構造的に追随せずズレる**実装は指摘対象。単純なコピペではなく「A を変えたら B も計算し直す必要があるのに、B が独立した定数になっている」パターン
- **要素の欠落・条件分岐に対する耐性**: 「A がある前提で B を決めている」実装で、A が条件分岐(フラグが false・リストが0件など)で存在しないケースを**明示的に確認したか**。A の不在時に B が崩れる/意味を失う実装は指摘対象。**「今の実装がたまたま壊れて見えない」は『確認した』とみなさない**
- **変更波及範囲**: 「次にこの仕様が変わるとしたら触る箇所は何ファイルか」を1つ言えるか。**1機能の変更が無関係なファイルに波及する設計は重大**
- **過剰設計**: 現時点で使われていない汎用化・将来のための抽象化を先回りしていないか(スコープ最小の方針違反。軽微〜重大は影響度で判断)
- **重複コピペ**: 同種の分岐・処理が**3箇所以上**コピペされている場合のみ指摘する(2箇所での抽出強制は過剰設計になりやすいため対象外)

**表示を持つ場合は加えて**:

- **固定サイズ × 可変コンテンツ**: 固定の高さ・幅などが、文字サイズ・文字数・言語による文字幅の違いといった可変要素を想定しているか。想定していないなら、**その値が実際には変わらない根拠**(常に固定桁数の数値である等)を示せるか。示せなければ指摘対象
- **無関係な要素間の暗黙の依存**: ある要素が意図的に自分のコンテナ境界を越えて配置される実装(負のオフセット・はみ出し前提など)が、別の場所の間隔の定義と暗黙に依存関係を持っていないか

### 5-3. テストの実効性(在って緑でも検証になっていない2つの形)

どちらも**「テストが無い」という形では現れない**ので、テスト一覧を眺めても気づけない。

- **実行されていない分岐** — 実行環境・設定・ビルド構成で分かれる仕様は、テストが**書かれていてもその回で実行されなければ踏まれない**。どの実行がどちら側を踏んだかを指せること
- **区別できない分岐** — **既定へ委譲する経路**(自分のコードが何もせず、OS・フレームワーク・上位のハンドラ・既定値に処理を渡す経路)は、**自分のコードが存在しない/壊れている場合と結果が区別できない**。素通しするミドルウェアは、登録されていなくても同じレスポンスを返す。**区別できるケース**(自分のコードが実際に手を出す側、または自分だけが出す副作用)が別に要る

### 5-4. コードを変えたときの完了条件

上の観点を**見ただけでは足りない**。次を満たして初めて、コードの変更を完了と言える。

- **静的検査(型チェック・Lint など、あるものだけ)とテストが green**。**実行して確認済みであること** — 実行していないなら「未検証」と書く(→ この節の冒頭。green は最低ライン)
- **新規ロジックにテストがある**(または不要な理由を明記)。そのテストが実際に効いているかは → §5-3
- **エラー経路・エッジケースが処理されている**(「ハッピーパスのみ」ならそう明記)。対象は → §5-1

**成果物の種類を問わない条件は [working-norms.md](working-norms.md) の「報告の基準」。** ここはそのコードに固有な追加分。

## 6. レビュー基準(セルフレビュー・他者コードレビュー共通)

**後から誰も気づけないものから順に見る。** 下位ほど、壊れることで気づける(静的検査・テスト・バグ報告)か、後からいつでも直せる。**検出のされにくさが同程度なら、どのタスクにも当てはまるものを先に置く。**

**上から見るのは、上位が下位の前提になっているから。** 仕様と違うものを作っていたなら、その実装のエッジケースを詰める意味はない。逆順にやると、意味の無くなる作業に先に時間を使い、途中で打ち切ったときに失うものが最大になる。

1. **仕様との一致**: そもそも要求されたものか。要求されていないものが入っていないか。仕様にある要素の欠落も見る。**間違ったものを作った場合、テストもその間違いに沿って書かれるので、気づく経路はレビューしかない**
2. **機能間の論理矛盾**: 新機能が既存機能と両立するか(例: 一覧の手動並べ替えと、保存時の自動整列は共存できない)。**diff だけ見ても分からない** — 交差する既存機能を列挙して突き合わせる。両方が実際に使われるまで表に出ない
3. **テストの中身**: 「意味のあるアサーション」か。通るだけのテストを弾く。**仕様の場合分けごとに、それを踏むテストの行を指せるか**を見る。指せないものは未検証(→ §5-3)
   - **テストの本数や緑であることは根拠にならない。** 網に穴があること自体は、穴を通った欠陥が出るまで分からず、しかもその欠陥は「テストが緑だから大丈夫」を根拠に見逃される — 気づける経路が無いどころか、**偽の安心を供給する**
   - **手順1と見るものが同じ**(仕様の主張を列挙して突き合わせる)なので、その列挙をそのまま使う
   - 人が書き継ぐなら「誰かが以前の決まりを覚えていて、レビューで気づく」という経路がある。**将来の変更を、そのときの経緯を知らない書き手が毎回行うなら、その経路は無い** — 残るのは書かれていて機械的に効くものだけで、つまり**仕様を保持しているのはテストだけ**になる
4. **確定事項の侵食**: 一度「議論済み・蒸し返さない」として決着させた事項に反していないか。**決めたことを実装が静かに巻き戻していないか**を見る。決定記録には自動的な強制が無いので、決めた本人が偶然読み返すまで表に出ない
   - 検出のされにくさは3と同程度で、**当てはまるのが「決着済みの領域に触るタスク」に限られる**ので後。触っていないなら該当なしでよい
5. **仕様変更に耐えられる作りか**: → §5-2。**今は動くので誰も気づかず、次に触るまで表に出ない。** その頃には上に実装が積まれていて、直す範囲が広がっている
6. **複雑さの逃がし**: 内部で吸収できる複雑さを、モード切替・設定項目・分岐としてユーザーや呼び出し側に露出させていないか(→ §1-2)
7. **契約変更の波及**: 呼び出し元・テスト・保存データ・ドキュメントまで追随しているか。**壊れることで気づける**(静的検査・実行時エラー)が、ドキュメントだけは壊れないので取り残される
8. **エッジケースと失敗経路**: → §5-1。エラー時に中途半端な状態が残らないか。**壊れることで気づける**(バグ報告)
9. **読みやすさ・規約**: **最後に見る**。既存コードとの一貫性 > 個人の好み。いつでも直せる

承認前の儀式: 「この変更で壊れうる最悪のケースを1つ挙げる」。挙げられないなら理解が足りていない。

### 6-1. 指摘として出してよいものの基準

**「根拠を示せる」とは、機械的パターン(grep 等で検出できる形)に落とし込めることではない。** 該当ファイル・行を指し、「この実装は◯◯という前提に依存しており、△△が変わると××が破綻する」という**具体的な破綻シナリオ**を、判断・推論を交えて説明できれば、それは印象論ではなく根拠のある指摘である。

逆に「読みにくい」「もっと綺麗に書ける」のように破綻シナリオを示せない指摘は、**印象論として却下する**。

**「該当ファイル・行」と「何が変わると何が壊れるか」を明示できないものは指摘しない。**

## 7. バグを見つける・直す考え方

1. **再現が最優先**: 再現できないバグは直せたかどうかも分からない。再現手順を最小化する(データを減らす、手順を減らす)。
2. **差分思考**: 「最後に動いていた状態」との差分を疑う。`git log` / `git bisect` は勘より速い。
3. **仮説→検証のループ**: ログや print は「仮説を検証するため」に入れる。闇雲に散らばせない。仮説を1文で書けないならまだ観測が足りない。
4. **原因を説明できるまで直さない**: 「なぜかこれで直った」は直っていない。パッチが効いた理由を説明できない修正は、別の場所で同じバグが再発する。
5. **横展開**: 1つバグを直したら、同じパターンを grep して同型のバグを探す。バグは群れで存在する。
6. **修正は再現テストとセット**: 先に落ちるテストを書き、修正で green にする(§10)。

---

## 8. リファクタリングの判断基準

- **やる条件**: ①その場所を機能追加・バグ修正で触る必要がある、②同じ構造の重複が3回目に達した、③現に理解を妨げている(読むたびに罠にはまる)。
- **やらない条件**: 「気に入らない」「自分ならこう書く」だけの動機。動いていて触る予定のないコード。
- **やり方**: 動作変更と絶対に混ぜない(コミット分離)。テストがないコードのリファクタリングは、先に現状の挙動を固定する特性テストを書いてから。挙動が変わったかどうか判定できない状態でリファクタリングしない。
- 依頼されたタスクの途中で見つけたリファクタリング機会は、実施せず「提案」として報告に添える。

---

## 9. パフォーマンス改善の判断基準

- **計測前に最適化しない**。推測で書いた最適化は複雑さだけ残して効かないことが多い。
- 直す価値があるのは「ユーザーの体感」か「金銭コスト」に効くものだけ。
- 優先順位: ①アルゴリズム・クエリ(N+1、O(n²)、全件フェッチ) ②I/O回数(ネットワーク往復、再レンダリング) ③マイクロ最適化(ほぼやらない)。
- クライアント側に状態を持つ設計では「同期のペイロードサイズ」と「起動時の読み込み量」が効きやすい。リスト表示は仮想化を先に検討。
- 最適化したら before/after の数値を報告に含める。数値がない最適化報告は無効。

---

## 10. テスト戦略

- **振る舞いをテストする。実装をテストしない。** 内部のプライベート関数の呼び出し回数を assert するテストはリファクタリングを妨害するだけ。
- 厚く書く場所: 純粋ロジック(日付計算、並べ替え、導出値、状態遷移)。薄くする場所: UI の見た目、外部APIのラッパー。
- **バグ修正は再現テスト先行**: まず落ちるテストを書く → 修正 → green。これで「直った」ことが証明され、再発も防げる。
- テストが書きにくいと感じたら、それはテストの問題ではなく設計の問題(依存が多すぎる、I/Oとロジックが混ざっている)。設計を直すシグナルとして扱う。
- テスト名は「何をしたら何になるべきか」を日本語または文で書く(`日付を跨いで登録したとき終了日が翌日になる`)。落ちたとき名前だけで壊れた仕様が分かるように。

## 11. エラー処理方針

- **境界で捕捉し、内部では伝播させる**: try/catch はシステムの境界(UIイベントハンドラ、APIハンドラ、ジョブのエントリ)に置く。内部の各層で握りつぶさない。
- **握りつぶし禁止**: `catch { /* ignore */ }` を書くときは、無視してよい理由をコメントで書けなければ書いてはいけない。
- ユーザー向けメッセージ(何が起きて何をすればよいか)と開発者向けログ(スタック、コンテキスト)を分離する。ユーザーに例外の生文字列を見せない。
- 失敗したら中途半端な状態を残さない。複数ステップの書き込みは「全部成功 or 元通り」に。クライアント側に状態を持つ設計では特に、壊れた中間状態が同期で増殖する。
- リトライは冪等な操作にだけ入れる。冪等でない操作のリトライは二重実行バグの温床。

## 12. 命名規則

- **名前は嘘をつかない**: `getUser` が作成もするなら名前が嘘。処理を変えたら名前も変える。
- 単位・基準を名前に含める: `durationMinutes`、`departAtLocal`、`priceJpy`。単位のない数値名(`timeout`, `size`)は事故のもと。
- boolean は `is/has/can/should` + 肯定形。`isNotReady` のような否定形は二重否定を生むので禁止。
- 型・スキーマの名前はドメインの言葉(仕様書に出てくる言葉)をそのまま使う。仕様が「アイテム」ならコードも `Item`。翻訳・言い換えは仕様とコードの対応を壊す。
- 一貫性 > 正しさ: 既存コードベースが別の規約なら既存に従う(直したければ別途一括で)。

---

## 13. コメントを書く基準

- 書くのは「コードで表現できないこと」だけ: **why(なぜこうしたか)、制約(なぜ他の方法ではダメか)、外部要因(APIの仕様バグ、OSの制限)**。
- 書かないもの: コードの逐語訳(`// ユーザーを取得する`)、変更履歴(git が持っている)、レビュアーへの言い訳(「この変更で正しくなります」)。
- TODO には「何を・どういう条件になったら」を書く(`TODO: 認証方式の決定後にトークンの保存先を差し替える`)。条件のない TODO は永遠に残る。
- 仕様上の決定番号(D-N)や issue への参照をコメントに残すと、あとから「なぜ」を辿れる。

---

## 14. ドキュメント更新ルール

- 仕様に影響する変更は、コードと**同一コミット**で spec / README / CLAUDE.md を更新する。
- ドキュメントは常に最新版のみ(ファイル名に版数を付けない)。履歴・差分は git tag / git diff で取る。差分ファイルを別途保存しない。
- 決定は D-N 番号で管理: 新しい決定は新番号、既存決定の変更は同番号のまま内容更新+変更履歴を1行。未決事項も同じ体系で「保留」として管理する。
- 決定のバッチごとにドキュメントのバージョンをインクリメントし、「vX.Y での主な変更点」を数行で記録する。
- CLAUDE.md の「現在のステータス」「次のアクション」はセッション終了時に現実と一致していること。
