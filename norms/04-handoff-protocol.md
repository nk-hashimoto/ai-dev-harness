# AI間引き継ぎプロトコル

> 作業途中で別のモデル・別のセッションへ引き継ぐとき、品質を落とさずに続行するために「何を残すか」の整理。
> テンプレートは [templates/handoff.md](templates/handoff.md)。

---

## 1. 原則: 引き継ぎ先は「何も覚えていない優秀な同僚」

引き継ぎ先が上位モデルなら、この「優秀な同僚」の想定はさらに強くなる: **作業手順を刻んで渡す必要はなく、ゴール・制約・スコープ外・地雷を一度に渡して走らせる**のが最も結果が良い(→ [05-orchestration-notes.md](05-orchestration-notes.md) §3)。検証手順は §8 のコマンドを載せるだけでよく、「検証ステップを入れること」自体を指示する必要はない。

引き継ぎ先は、コードとドキュメントを読む能力はあるが、**会話の経緯・暗黙の合意・試して捨てた案を一切知らない**。したがって残すべき情報は「リポジトリを読んでも分からないこと」に集中する。リポジトリを読めば分かること(ファイル構成、コードの内容)を handoff に書くのはノイズであり、正が二重になる分むしろ有害。

## 2. 残すべき情報(優先度順)

1. **ゴールと完了条件**: このタスクは何ができたら終わりか。1〜3文。これがないと引き継ぎ先は「もっともらしい別のゴール」に向かう。
2. **現在地**: 完了したこと / 進行中のこと(どこまで書けているか) / 未着手のこと。進行中の作業は「次の一手」を具体的なファイル・関数名レベルで書く。
3. **ユーザーの未実行の指示**: ユーザーが決めたが、まだ着手していないこと。「Xが終わったらYをやりたい」という順序の指定、保留の条件、後回しにした依頼、現タスクの外に置いた宿題。**会話にしか存在しない**ので、落とすとユーザーが同じ指示を言い直すことになる。
4. **決定事項とその理由**: セッション中に下した設計判断と、**なぜ他の案を捨てたか**。理由がないと、引き継ぎ先が善意で捨てた案を再採用する。
5. **試して失敗したこと**: 「Xを試したがYの理由でダメだった」。これが最も失われやすく、最も再発コストが高い情報。
6. **未決事項・保留**: 決めていないこと、ユーザー確認待ちのこと。「決めていない」と「決めた」の区別が曖昧なまま引き継ぐと、仮置きが既成事実化する。**判断が既にあって未実行のものは項目3へ** — ここに書くのは判断そのものが存在しないもの。
7. **地雷・注意点**: 触ってはいけない場所、壊れやすい箇所、一見不要だが消してはいけないコード、環境の罠(ビルドの癖、flaky なテスト)。
8. **検証方法**: 動作確認のコマンド・手順。引き継ぎ先が「動く状態を維持しているか」を随時確認できるように。
9. **正のドキュメントの所在**: 仕様はどれが正か、どのバージョンか。

## 3. 引き継ぎ時にやること(引き継ぐ側)

1. **きりの良い状態にする**: 可能ならビルド・テストが green の状態で渡す。無理なら「何が red で、なぜか」を明記。中途半端な編集は revert するか、WIP コミット + 説明で残す。
2. **handoff.md をテンプレートから書く**(所要10分以内を目安。長すぎる handoff は読まれない)。
3. **未コミットの変更を整理する**: `git status` がクリーンか、そうでなければ各変更ファイルの意図を handoff に記載。
4. **ドキュメントの整合を回復する**: CLAUDE.md の「現在のステータス」を現実に合わせる。handoff.md に書くべきことと CLAUDE.md に書くべきことを混同しない(handoff = このタスク限りの状態 / CLAUDE.md = プロジェクトの永続文脈)。

## 4. 引き継がれる側の開始手順

1. handoff.md → CLAUDE.md → 正の仕様の該当箇所、の順で読む。
2. `git log --oneline -10` と `git status` で handoff の記述と現実が一致しているか照合する。**一致しなければ handoff を疑い、現実(git)を正とする。**
3. 検証コマンドを実行して「動く状態か」のベースラインを確認する。
4. 「次の一手」から着手する。handoff に疑問があれば、推測で埋めずユーザーに確認する。

## 5. handoff.md の運用ルール

- 置き場所: リポジトリ内なら `docs/handoff/YYYY-MM-DD-<topic>.md`(またはプロジェクトの慣習に従う)。タスク完了後は削除するか、内容を正規ドキュメント(spec / CLAUDE.md)に昇華して消す。**handoff.md を第二の仕様書にしない。**
- 1 handoff = 1 タスク。複数タスクの状態を1ファイルに混ぜない。
- 会話ログの貼り付けは禁止。要約・構造化された情報だけを書く。
