# 承認プロンプトを減らす(Claude Code)

> Claude Code の権限設定を前提にしている。Codex と Kiro の承認・許可の設定は、各ツールの公式ドキュメントに従う(Kiro は role 定義の `permissions` と `trustedAgents`。`adapters/kiro/runtime.md`「role の起動と再開」)。

自動承認(auto mode)や許可のバイパスが使えない環境では、実装ループの1周ごとに**コマンドの数だけ承認**が要る。ここを放置すると、無人で回すどころか有人でも張り付きになる。

## 1. まず allowlist を試す

[`adapters/claude/settings.json.template`](../../adapters/claude/settings.json.template) を、プロジェクトの `.claude/settings.json` にコピーして当てる。  
読み取り専用のコマンド(`git status` / `git diff` / `ls` / `grep` など)、主要な言語エコシステムの検証コマンド、スキル `parallel-tasks` が使う worktree の作成・移動・削除を事前許可している。

**使わないエコシステムの行は削る。** 許可リストは短いほど、何を許したかを人が把握できる。

**組織のポリシーによっては、この設定自体が無効化されていることがある。** 効いているかは次で判定する。

1. 設定を当てる
2. セッションを開始し、`git status` を実行させる
3. **承認を求められなければ効いている。求められたら効いていない**

効いていない場合、原因は managed settings による上書きか、`allow` の記法がそのバージョンで解釈されていないかのどちらか。前者は管理者に確認するしかない。

## 2. 効かない場合(および効いても効く)— コマンドを束ねる

**検証コマンドを1本にまとめる。** 3回の実行は3回の承認だが、1本なら1回で済む。

```
make verify        # 中身: lint && 型チェック && テスト
```

**まとめる先はリポジトリに置く** — `Makefile` のターゲット、そのエコシステムのタスクランナー、あるいはリポジトリ内のスクリプト。どれでもよいが、**プロンプトに書かない**(次のセッションに届かない)。

こうしておくと、実装ループもエージェント定義も「そのリポジトリの検証コマンド1本」を指すだけで済み、言語が違うサブシステムでも同じ書き方が通る。

## 3. 委譲の粒度を大きくする

自動承認がない環境では、**委譲するほど承認ポイントが分散する** — サブエージェントの実行するコマンドにも承認が要るうえ、どのエージェントの要求なのかが画面上で追いにくくなる。

したがって **1タスク = 1委譲**に寄せる。タスクを細かく割って何度も委譲するより、1タスク分をまとめて渡し、承認は「実装1回分 + 検証1回分」に集約する。

これは委譲の判定基準そのものとも整合する(→ `shared/norms/working-norms.md`「委譲・スコープ・分量」)。数手のツール呼び出しで終わる仕事はもともと委譲しない。

## 4. 承認を求められた側の作法

**承認が拒否されたら、同じコマンドを言い換えて再試行しない。** 拒否は「そのコマンドを実行してほしくない」という意思表示で、引数を変えて通そうとするのは意図に反する。何をしたいのかを説明し、代わりの手段を提案する。

## 5. この allowlist はセキュリティ境界ではない

`settings.json.template` の `allow`/`deny` は**承認プロンプトを減らすための利便性設定**であり、秘密情報を守るサンドボックスではない。以下を前提として運用する。

- **`Read` への `deny`(`.env` / `*.pem` / `id_rsa*`)は `Bash` 経由のアクセスには効かない。**
  - `Read` と `Bash` は別名前空間の許可リストで、`Bash` 側のコマンド一致は「コマンド文字列の前方一致」でしかなく、引数の途中に現れるファイルパスを構造的に認識できない。
  - `Bash(cat:*)` は `.env` を丸ごと出力できてしまうため allow から外した。ファイルを覗く用途は `Read` ツール(deny を正しく守る)で代替できるので実用上の損失はない。
  - `head`/`tail` は `command | tail -50` のようなパイプ用途が多いため allow に残し、`cat .env` / `head .env` / `tail .env` の素朴な呼び出しだけを `deny` で個別にブロックした。これは網羅的な防御ではない。`head -n5 .env` のようなオプション付き呼び出しや、`grep`/`sed`/`awk`/`diff`/`python -c` など他コマンド経由の迂回は防げない。狙いはプロンプトインジェクション(リポジトリ内の指示文が「`cat .env` を実行して」と誘導する等)による最も素朴な誘いを塞ぐことで、迂回を狙うエージェント・攻撃者を止める設計ではない。
  - 秘密情報を確実に守る必要があるなら、この allowlist に頼らず①作業ツリーに実際の値を含む `.env` を置かない(`.env.example` のみをコミット・チェックアウトする)、②Claude Code の sandbox 機能(`sandbox.credentials.files` の `deny`/`mask`)でプロセス層から遮断する、のいずれかを使う。後者は本テンプレートの前提(hooks も sandbox も使わない)の外側にあり、別途の導入が要る。
- **`Bash(make:*)` / `Bash(npm run:*)` のような無制限ワイルドカードには戻さない。**
  - `make <target>` / `npm run <script>` はリポジトリの `Makefile` / `package.json` に書かれた中身をそのまま実行するため、ターゲット名を無制限に許可すると未知のターゲットも無承認で実行できてしまう。
  - テンプレートは `make verify` / `make test` / `npm run test` など具体的な名前だけを allow しているが、これはターゲット名の narrowing であって任意コード実行そのものへの対策ではない。`test`/`lint`/`build` は最も標準的で自動実行されやすいターゲット名でもあり、`Makefile` の `test:` や `package.json` の `scripts.test`(あるいは npm の `pretest`/`posttest` のようなライフサイクルフック)自体が汚染されていれば、名前を絞っていても無承認で実行される。
  - この allowlist は「このリポジトリの `make test` を自分の手で叩くのと同じ信頼度で実行してよい」という利用者の判断に委ねるものだと理解して使う。その信頼を持てないリポジトリには適用しない(もしくは make/npm run の行を削り、都度承認に戻す)。
  - 新しいターゲットを使うようになったら個別に allow へ足す(既存の行を `*` に広げない)。見覚えのないターゲット名の承認を求められたら、それ自体が異常の兆候であることを踏まえて中身を確認してから許可する。ただしこれは「知らないターゲットの取りこぼし」への防御であって、`test`/`build` 自体が汚染された場合の防御ではない。
  - スクリプトの中身を実行前に検査する、あるいはネットワーク送信先を制限して実害を限定する(`sandbox.network.allowedDomains` 等)には hooks や sandbox の追加導入が要り、本テンプレートの前提の外側にある。この harness は現時点でこのリスクを閉じる手段を持たない。
