# MR / PR フロー

## 導入時に決めること

プロジェクトの `WORKFLOW.md` §3に、本流・ブランチ規則、MR/PRの作成・照会方法、必要な承認、台帳更新の共有方法を記入する。雛形は [WORKFLOW.md.template](../../kit/docs-dev/WORKFLOW.md.template)。

規約が無いときの既定は、MR/PRを提出して人のレビューへ渡すこと。別の着地を採る場合はプロジェクトの規約を実行時に読む。**AI reviewerの合格はマージの承認ではない。**

## 状態・進行・証跡の所在

| 確認したいこと | 正の定義 |
|---|---|
| 状態・依存・旧台帳からの移行 | [TASKS.md.template](../../kit/docs-dev/TASKS.md.template) → 導入先の台帳 |
| 状態照合、実装、差し戻し、中断・再開 | [next-task](../../kit/skills/next-task/SKILL.md) |
| プロジェクト固有の提出・承認・台帳保存 | 導入先の `WORKFLOW.md` §3 |
| 人のレビューに渡す検証・判断の記録 | 導入先の `WORKFLOW.md` §7 |

MR/PR提出後はレビュー中として残し、次の実行でホストの実状態と照合する。マージ済みだけで自動的に完了とせず、必要な検証・承認も確認する。依存のない別タスクを進める場合も、実装対象ファイルの重なりを確認する。

## リポジトリごとの規則の解決

作業対象ディレクトリの `CLAUDE.md`、上位の規約、貢献ガイド、既存ブランチの慣習から特定する。ブランチ命名等が読み取れなければ聞く。サブシステム固有の値をグローバルのスキルへ埋め込まない。

GitLab / GitHub / GitHub Enterpriseの違いは、作成・照会に使うCLI/APIや権限設定で吸収する。hooksは必要としない。人のレビューはセッション出力とAIへのインタビューで進めてもよいが、マージ判断に使った要点はMR/PRに保存する。
