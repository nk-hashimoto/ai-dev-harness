# MR / PR フロー

## このハーネスが定めること

**停止点だけ**を定める。しかもそれは**プロジェクトが着地の規約を持っていないときの既定**で、規約があればそちらが優先される(`/next-task` 手順8)。

- タスクが1件完了したら、コミットして push し、MR/PR を作る
- **自動マージしない。** レビュー担当エージェントの「合格」は、マージの承認ではなく**人のレビューへ出せる状態になったこと**の判定
- MR/PR を作った時点でループは止まる。`/loop` で回している場合、次のタスクへは進んでよいが、**直前のタスクと同じファイルを触るタスクは、MR がマージされるまで着手しない**(未マージの変更の上に積むとレビューの単位が崩れる)

**別の着地(マージまで自動で行う等)を採るプロジェクトは、それを開発ワークフローの文書に書く。** 手順8はそこを読んで従うので、既定を上書きするのに規範やスキルを書き換える必要はない。ただし**「合格 ≠ マージの承認」だけは既定ではなく、どの着地でも変わらない** — マージしてよい根拠は、レビュー担当の判定ではなくプロジェクトの規約が持つ。

## このハーネスが定めないこと

**ブランチ命名規則・MR テンプレート・レビュー担当の割り当ては、ここに書かない。**

モノレポでは、これらがサブシステムごとに違う。トップレベル(`~/.claude/` やこのハーネス)に特定の値を埋めると、**当たらないサブシステムで黙って間違ったブランチが切られる**。

代わりに、**実行時に解決する**。`/next-task` の手順2と手順7がこれを行う。

1. 作業対象ディレクトリを起点に、**そのディレクトリの `CLAUDE.md`** を見る
2. 見つからなければ、上位ディレクトリの `CLAUDE.md`、リポジトリの貢献ガイド、MR/PR テンプレートの置き場を見る
3. 既存ブランチの命名を `git branch -a` で見る
4. **どれからも読み取れなければ、推測せず止まって聞く**

したがって、サブシステムごとの規則は**そのディレクトリの `CLAUDE.md` に書く**のが正しい置き場になる。触ったときだけ読まれるので、他のサブシステムのコストにならない。

## ホストに依存しない書き方

MR/PR を作る操作は、**そのリポジトリで通っている方法に従う**。特定の CLI やホストをこのハーネスに固定しない。

- ホストが変わっても(GitLab → GitHub Enterprise など)、上の停止点の定義は変わらない
- 変わるのは「作る操作」だけで、それはリポジトリ側の規約として読み取る

## 人のレビューをどこまでやるか

これはハーネスの外の運用判断。**ハーネスは「人のレビューに出す」ところまでしか保証しない。**

レビューを軽くする方向に運用する場合でも、**マージを自動化しない**ことは維持する価値がある。エージェントのレビュー担当は仕様適合と論理矛盾を見るが、「そもそもこの変更を今入れてよいか」(リリース判断・他チームとの調整・優先順位)は見ていないため。
