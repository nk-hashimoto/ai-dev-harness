# parallel-tasks — 複数タスクを同一セッションで並列に消化する

**人が明示的に呼んだときだけ動く。自動起動しない。** 他の作業の最中に始めると本題が逸れる。

`next-task` が1回1タスクで進める工程を、**タスク単位の worktree に分けて同時に走らせる**。
**検証・レビュー・提出・完了判定は `next-task` の手順4〜9を使う**(マージの順序だけ手順6で変える)。このスキルが持つのは、その前後にあるトラックの切り方・worktree の扱い・マージの順序・止め方だけ。

実装を並列にするのは、`session-economy` と `02-thought-processes.md` が既定とする「並列は読み取り系だけ」から外れる例外である。外れてよいのは、**worktree でトラックを分け、トラック間で触るファイルが重ならず、マージを1本ずつ直列に行う**ときだけ。

## 使える導入先

**`WORKFLOW.md` §3 が本流へのマージまでを定めている導入先だけ。**

- 同じトラックの次のタスクは、依存かファイルの重なりがあるので先行タスクのマージを待つ(`next-task` 手順1)。MR/PRを提出して止まる導入では、トラックの2件目以降が人のマージを待つことになる
- 起動の前に §3 を読み、①「提出時にすること」がマージまでを含む ②マージしてよい根拠が書かれている、の両方を確かめる。**AIレビューの合格はマージの承認ではない**(`next-task` 手順8)ので、根拠は §3 の規約に求める
- どちらかを満たさない、または読み取れないときは、**起動せず**「この導入では使えない。`next-task` を使う」と報告して止まる。読み取れないものを許可と読まない
- worktree を作れる実行環境だけで使う。作れるか未確認の環境は runtime adapter の定めに従う

## いつ使うか / 使わないか

- **使う**: 着手可能なタスクが複数あり、触るファイル集合が分かれているとき。重なるタスクは同じトラックへ直列に置く
- **使わない**: 着手可能なタスクが1件、または全てが同じファイルを触るとき → `next-task`。**1本で足りるなら1本**
- `next-task` の連続実行(1タスク1セッションの連鎖)とは併用しない。並列運転のコンテキストは、計画ファイルと毎タスクの読み直しで守る

## 起動時に人から受け取るもの

1. スコープ外のタスクID(予約済み・他の経路で進めているもの)
2. 停止条件(閉じるタスク数の上限、人が指定した終了時刻(例: 18時で止める)など)。runtime adapter が使用量の計測手段を定めていないとき、これが止める唯一の手段になる。**人が見ていない運転では、停止条件が決まらなければ並列を始めない**
3. 並列本数の上限(既定3。執筆時点の運用値で、導入時に見直す。上げるなら決めた人と理由を計画ファイルに残す)
4. adapter が使用量の閾値を定めているとき、それを変えるか。変えるなら決めた人・日付・値

受け取ったものは手順0の計画ファイルに書く。会話に残したままにしない。

## 手順

0. **使えるかの確認・土台・本流の検証**:
   1. 「使える導入先」の確認を行う。満たさなければここで止まる
   2. `next-task` 手順0(`git fetch`、本流との遅れの確認、土台を更新したときの指示ファイルと仕様の読み直し、台帳とMR/PRの照合)を行う
   3. `next-task` 手順4でリポジトリから特定した検証コマンドを本流で通し、全て合格することを確かめる。**不合格があれば、それを直すタスクを1本だけ直列で先に通す。不合格のまま並列を始めない**
   4. **計画ファイルを専用ブランチの worktree に書いて git で守る**。ブランチは `plan/parallel-tasks-<日付>`、本流から切る。`<worktree-root>` はリポジトリの外 `../<リポジトリ名>.worktrees/`(規範「同じマシンで複数セッションを走らせるなら」)。リポジトリの中に置くなら `.gitignore` へ入れる

      ```bash
      git worktree add <worktree-root>/plan -b plan/parallel-tasks-<日付> origin/<本流ブランチ>
      ```

   - 計画ファイルの置き場は `handoff` スキルの既定に従い、`docs/handoff/<日付>-parallel-tasks-plan.md` とする(プロジェクトに慣習があればそれ)
   - 書くもの: 受け取った項目、トラック表、各トラックの現在地、手順1〜6のチェックリスト、adapter が使用量を計測するなら計測の記録
   - 状態が変わるたびに更新してコミットする。中断や環境の回収をまたいで残すなら、計画ブランチを push する。**計画ブランチは本流へ取り込まない**
   - 計画ファイルの先頭に、意味が分からなければこのスキルを読み直す旨を書く。未完了のトラックが残るなら、そのファイルが次の実行の引き継ぎになる。全て終わったら worktree を外す

1. **選定とトラック割り**: 資格判定は `next-task` 手順1のまま。資格のあるタスクからスコープ外を除き、`#### 内容` と `#### spec` から触るファイル集合を見積もる。重なるタスクは同じトラックへ直列に並べ、トラックは上限本数までにする
   - `#### impl` が `advanced` のタスクや、契約(型・スキーマ・永続化形式)を変えるタスクに依存するものは、同じトラックの後ろへ置く
   - 見積もりが外れて2本が同じファイルを触ると分かったら、後から取る方を待たせ、先行トラックのマージ後に worktree を切り直す
   - 台帳の種別の優先順はトラックに入れるタスクの選定に使い、トラック内の順序は依存関係で決める

2. **worktree を切る**(トラックの最初のタスク):

   ```bash
   git worktree add <worktree-root>/T-xxx -b <ブランチ名> origin/<本流ブランチ>
   ```

   - ブランチ名は `next-task` 手順2で特定した規約に従う。ディレクトリ名はタスクIDにする
   - 依存のインストールが要るプロジェクトでは、その worktree で行う(worktree 間で共有されない)
   - トラックの2件目以降は、先行タスクのマージ後に、同じ worktree を新しいブランチへ付け替えて使い回す。作業ツリーが clean であることを確かめてから行う

     ```bash
     git worktree move <worktree-root>/T-xxx <worktree-root>/T-yyy
     git -C <worktree-root>/T-yyy checkout -B <新ブランチ名> origin/<本流ブランチ>
     ```

     - `.gitignore` 済みの依存ディレクトリ(`node_modules` 等)は残るので、インストールをやり直さずに済む。先行タスクのブランチは消えない
   - **メインのチェックアウトでは、実装も台帳更新もしない**

3. **毎タスクの読み直し(無条件)**: 委譲の直前に、計画ファイルと台帳の当該タスク節の全文を読み直す。要約の有無を条件にしない。終了時刻の指定があれば `date` で現在時刻を取る

4. **実装委譲**: `next-task` 手順3の role 選択と起動の規則を守る。違いは次の3点。
   - runtime adapter が定める**バックグラウンド起動**で、完了を待たずに複数トラックを同時に走らせる
   - プロンプトに worktree の絶対パスを書き、その中だけで作業するよう明記する
   - 検証の出力は、自分の worktree のものだけで判定する。他トラックの編集中の不合格で完了を止めない

5. **検証・レビュー・提出準備**: `next-task` 手順4〜7を、トラックごとに worktree で行う。レビューも adapter のバックグラウンド起動で、worktree の絶対パスを渡す
   - 止まった・止められた implementer / reviewer は、新規起動の前に同じ体への続行(`next-task` 手順3・5)を試す。続行できず新規起動したときは、その理由を計画ファイルに書く
   - 指摘の未解消回数が3回に達して `#### ⚠要人間確認` が付いたタスクは、作業ブランチに残す。そのトラックは、依存しない次のタスクへ進む。依存していればトラックを終了する

6. **マージと完了**: `next-task` 手順8(§3に従う提出。ここではマージまで行う)を、順序だけ変えて行う。**台帳の更新より先に、最新の本流を取り込む。**
   1. 作業ブランチへ最新の本流を取り込む。共有ドキュメント(台帳・決定記録)を含め、衝突は相手側の更新を落とさず、自タスクの編集を載せ直す
   2. `git diff origin/<本流ブランチ> <作業ブランチ>` を読み、自タスクの変更だけが残っていることを確かめる。コードに変更があれば、`next-task` 手順4の検証を取り込み後の状態で全て再実行する
   3. 台帳と決定記録を更新してコミットする(§3の台帳の保存方法に従う)
   4. §3 が定める手順でマージする。**マージが競合や non-fast-forward で拒否されたら、1へ戻って取り込み直し、2〜3をやり直す。force push も、別トラックのマージを巻き戻す操作もしない**
   5. マージ後に `next-task` 手順0の完了判定(本流への取り込みの確認)を経て完了にする。計画ファイルの現在地を更新して次のタスクへ進み、全て終わったら worktree を外す

7. **報告**: `next-task` 手順9の書式に従い、タスクID・状態・要点・検証結果・レビュー判定・マージの有無・次の候補・飛ばしたタスクと理由を簡潔に返す。全トラック終了時は、作業ブランチに残したものと次の一手もまとめる

## 停止条件と使用量

- runtime adapter が使用量の計測手段を定めているときは、その指標・閾値・停止の定義が正。各サブエージェントの起動・続行の直前と、各サブエージェントの完了直後に測り、計画ファイルへ記録する
  - 閾値に達したら、新規タスクと新規エージェントを始めない
  - 走行中の同じタスクを収束させるための、既存 implementer / reviewer への続行は、計測と記録をしたうえで許可する
- 定めていないときは、起動時に受け取った停止条件に従う
- 終了時刻が指定されたら、新規着手を止める時刻・走行中を畳み始める時刻・全マージを終える時刻を、直近のタスクの所要から逆算して計画ファイルに書き、それに従う

## サブエージェントが黙って死んだとき

最終報告が無い(使用枠の切れ等)ときは、worktree の status と diff を読み、通った範囲だけを検証して論理コミットにまとめる。何を確かめたかは推測で埋めない。生きている別トラックを二重に起動せず、同じ体の続行を先に試す。

## 地雷

- 本流のブランチやメインのチェックアウトの上で、直接実装しない
- 並列本数は上限を守る
- マージ先を巻き戻す操作で、拒否を解消しない
