# decision-log — 決定・未決事項の起票

決定の**経緯**を追跡可能にする。「決まったこと」だけでなく「捨てた代替案」と「なぜ」が本体。

**引数**: 決定(または保留)の内容、候補案、理由。

## 手順

1. **記録先と採番の流儀を特定する**。プロジェクトの既存の決定記録(spec の決定一覧、`docs/adr/`、AGENTS.md の未決事項、`DECISIONS.md` 等)を探し、その形式・番号体系(D-N / ADR-NNNN)に合わせる。既存がなければ形式を1つ提案してから作る。
2. **既存番号との重複を確認する**。同一テーマの決定が既にあるなら、**新番号を切らずにその項目を更新する**(「決定 → 再検討 → 変更」の履歴が1箇所に集まる形にする)。
3. **本文を書く**:
   - **決定の場合**: 決めた内容 / 理由 / **捨てた代替案とその理由** / 影響範囲(どのコード・どの仕様節に効くか)
   - **保留の場合**: 何が決まっていないか / 判断に必要な材料 / **再開条件**(どのフェーズになったら、何が分かったら) / **当面の代替策**(保留中どう動くか)
4. **関連ドキュメントを同一コミットで更新する**(P9): 仕様書の該当節、AGENTS.md の「現在のステータス」「未決事項」、README の一覧など。決定番号への参照が新旧で食い違わないか grep で確認する。
5. 仕様の版数を上げる運用があるプロジェクトでは、バージョンインクリメントとタグ付けが必要かを確認する(該当スキルがあればそちらへ)。

## 注意

- **「保留」も決定として扱う**。再開条件のない保留は永遠に保留になる。「いつ・何をもって再開するか」を必ず書く。
- 捨てた代替案を省かない。半年後に同じ議論を最初からやり直すコストは、3行書くコストより桁違いに高い。
- 日付は絶対日付で書く(「先週」「次のフェーズ」ではなく `2026-07-26` / `F3 着手時`)。
- 決定文はセッションに依存しない言葉で書く。「今回の変更で」「本レビューで」は後から読むと意味が消える。
