# contract-change — 契約変更の安全手順

**引数**: 変更したい契約と、変更後の形。

## 手順

1. **影響範囲を全列挙する** → スキル `impact-scan` を実行する。ここを飛ばして着手しない(P3)。
2. **旧形式が存在し続けるかを判定する**。次のどれかに当てはまれば **Yes**:
   - クライアント側に永続化されたデータがある(組み込みDB・キーバリューストア・ファイル)
   - 全クライアントを同時に更新できない(モバイルアプリの配布、複数端末同期、外部の API 利用者)
   - サーバとクライアントのデプロイが同時でない
   - 過去のデータをバックアップ・エクスポートから復元しうる
3. **No なら**: 一括変更する。全消費者を同一コミットで追随させ、根拠(なぜ同時更新が保証されるか)を1行残す。
4. **Yes なら段階戦略を立てる**。順序を入れ替えない:
   1. **読み込み側を後方互換にする**(新旧どちらの形式も読める)。デプロイして行き渡らせる。
   2. **書き込み側を新形式へ切り替える**。
   3. **(旧データが十分に移行された後)** 旧形式サポートを削除する。削除の条件(いつ・何を確認したら)を決定として記録する。
   - 破壊的な削除・改名は、まず「追加 → 両対応 → 旧を非推奨 → 削除」に分解できないかを考える。
5. **マイグレーションを書く場合**:
   - **冪等に書く**(2回走っても壊れない)。中断からの再実行を前提にする。
   - スキーマバージョンを持ち、適用済み判定をデータ側に残す。
   - ロールバック方法を決める(逆マイグレーション、またはバックアップからの復元手順)。
   - 実行前に対象データの実物を確認する(件数・想定外の値・NULL)。
6. **テストする**:
   - **旧形式のデータを読み込むテスト**(これが本命。固定のフィクスチャとして残す)
   - マイグレーションを2回連続実行するテスト(冪等性)
   - 新旧混在状態のテスト(段階4-1 の状態)
7. スキル `impact-scan` で挙げた全消費者・ドキュメントを更新し、同一コミットにまとめる。

## 注意

- **クライアント側に状態を持つ設計・同期システムでは「全端末が同時に更新される」前提を絶対に置かない。** 何ヶ月も起動されていない端末が、古い形式のデータを持ったまま復帰する。
- データを失う操作(列の削除、形式の一括書き換え)は、実行前に必ずユーザーに確認する(P8)。バックアップの有無も確認する。
- 「移行は次のリリースで」と分けるとほぼ実施されない。段階を分けるなら各段階を**タスクとして起票**し、削除段階に再開条件を書く。
