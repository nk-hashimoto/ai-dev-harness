# impact-scan — 変更影響範囲の調査

契約を変える前に、波及先を**着手前に**全列挙する(`~/.agent-norms/00-priority-rules.md` P3)。

**契約の定義は `~/.agent-norms/00-priority-rules.md` P3 が正。** 項目が増えることがあるので、ここに書き写さない。

**引数**: 変更予定のシンボル名、ファイル、スキーマ名のいずれか。

## 手順

1. **定義と全参照を洗う**。検索語を**複数用意**する:
   - シンボル名そのもの、および旧名(改名の場合)
   - re-export・エイリアス(`export { X as Y }`、`import ... as`)経由の別名
   - **文字列参照**: `"シンボル名"` / `'シンボル名'`(動的キー、リフレクション、設定ファイル、JSON のキー)
   - snake_case / camelCase / kebab-case の変換形(API境界やDB列名で表記が変わることがある)
2. **永続化・シリアライズへの到達を判定する**。以下に値が流れ込んでいないか追う:
   - DBスキーマ・マイグレーション
   - クライアント側の永続化(組み込みDB・キーバリューストア・ファイル・キャッシュ)
   - API リクエスト・レスポンスのボディ
   - 設定ファイル・環境変数・feature flag
   - ログ・分析イベントの名前(ダッシュボード側が壊れる)
3. **テストとフィクスチャ**を列挙する(スナップショット・ゴールデンファイル・モックを含む)。
4. **ドキュメント**を grep する(spec / README / AGENTS.md / API ドキュメント / コメント内の言及)。
5. **後方互換の要否を判定する**。「旧形式のデータ、または旧バージョンのクライアントが、変更後も存在し続けるか?」
   - Yes → 移行/互換戦略が**必須事項**。段階戦略はスキル `contract-change` へ。
   - No → 一括変更でよい。その根拠(全データが同時に更新される理由)を1行書く。

## 出力

- 影響箇所の一覧(カテゴリ別: 呼び出し元 / テスト・フィクスチャ / 永続化・シリアライズ / ドキュメント)
- 後方互換の要否と、その判定根拠
- 使用した検索語の一覧(取りこぼしを他者が検証できるように)

## 注意

- **動的参照は grep に掛からない。** キー名の文字列でも必ず検索する。
- **影響ゼロと出たら、検索語を疑う。** 本当にゼロなのは、追加したばかりの private なシンボルくらい。
- クライアント側に状態を持つ設計・複数端末の同期・利用者が自分で更新するアプリケーションでは、「全クライアントが同時に更新される」前提は置けない。
