# session-economy — role 配分を決める

**起動条件**: ユーザーが明示的に呼んだとき、または大きな作業の着手前に計画を立てるとき。

**前提**: 委譲は無料ではない。サブエージェントは毎回コールドスタートで、こちらが持っている文脈を再取得するところから始まる。**節約になるのは「大きく独立した仕事」を渡したときだけ。**

## 手順

1. **タスクを性質で分解する**:
   - 判断・設計・レビュー(契約を決める、トレードオフを選ぶ、成果物の可否を判定する)
   - 探索・抽出(広範囲の grep、一覧化、事実の収集)
   - 機械的な実装(契約が文章で書けている作業)
2. **委譲するかを判定する。委譲しないものを先に外す**:
   - 数手のツール呼び出しで終わる → **自分でやる**
   - **自分の作業の検証** → 委譲しない。検証は自分の工程
   - 契約(完了条件)を文章で書けない → 委譲できない。**まず自分で契約を固める**
   - 残ったもののうち、大きく独立して並列化できるものだけが委譲対象。**1体で足りるなら1体**
3. **role とモデルを割り当てる**(どのモデルが上位/下位か、role 定義の器と起動方法は runtime adapter の `runtime/<ツール名>.md` が正。先に読む):
   - 判断・設計・最終レビュー → 上位モデル(通常は親セッションのまま。独立レビューは reviewer role)
   - 通常の実装 → implementer(standard)。契約・永続化・複雑ロジックと重大指摘後の差し戻し → implementer-advanced
   - 単純な調査・抽出 → 読み取り専用の調査 role か軽量モデル(実装は任せない)
   - **割り当ての表現は定義側に置く。** モデルの世代は role 定義に完全な識別子で固定する。実行時にエイリアスでモデルを上書きしない(解決先が更新で変わる)。定義の無い汎用エージェントには世代を固定する手段が無いことが多いので、世代が問題になる委譲は先に定義を作る
     - 本文に何を書くか(スコープ固定・書くと逆効果な検証指示)は `~/.agent-norms/05-orchestration-notes.md`
4. **委譲プロンプトに4点セットを必ず入れる**(`~/.agent-norms/02-thought-processes.md` §7):
   1. 完了条件 2. 変更してよい範囲 3. **変更してはいけない範囲** 4. 検証方法
   - 委譲先が上位モデルなら、手順の細分化と検証ステップの明示は書かない(自前でやるので二重になる)。代わりにスコープ固定を強く書く。委譲先が下位モデルなら、逆に手順と検証を明示し、`~/.agent-norms/03-implementation-pitfalls.md` を読ませる。**この出し入れは呼び出し側(このスキルを実行している側)が決める** — 委譲先に自己判定させない
   - 詳しくは `~/.agent-norms/05-orchestration-notes.md`
5. **並列化は読み取り系のみ**。同じファイルを書く複数エージェントを同時に走らせない。
6. **結果を親でレビューする**。重点は「頼んでいない変更が入っていないか」。

## 出力

| 作業 | 実行者(モデル/エージェント) | 理由 | 完了条件 |
|---|---|---|---|

に加えて、委譲しないと決めたものとその理由(判断の記録として残す)。

## 注意

- **委譲の数を成果と取り違えない。** 委譲が増えるほど文脈の再取得コストと統合コストが増える。迷ったら自分でやる。
- サブエージェントは親と別のコンテキストで動くので、ログや中間出力のノイズを親に持ち込まない利点がある。**逆に、親が持つ暗黙の前提は伝わらない** — プロンプトに書いていない制約は守られない。
- エージェント間の報告は事実を削らない(判断材料になる)。短くするのはユーザー向けの文章とディスクに書く成果物の方。
