# spec-change — 仕様変更の確定・同期・タグ付け

**前提**: 仕様書への実質的な内容変更はすでに終わっている(または今まさに行う)こと。このスキルは、その変更を**確定させ、参照している全箇所に矛盾なく反映する**ための手順。内容の是非はこのスキルの範囲外。

## このスキルが置いている前提

プロジェクトの文書構成に依存する手順が混じっている。**無いものは飛ばしてよい**が、飛ばしたことを報告に書く。

| 前提 | 無い場合 |
|---|---|
| 仕様書が `vX.Y` 形式の版数を持つ | 手順2・3・4・5・11・12 を飛ばす。手順6〜10 だけで足りる |
| 決定記録が仕様書とは別ファイルにある | 手順1の振り分けを飛ばす。ただし**根拠と却下した案の置き場が無いなら先に作る**(スキル `decision-log`)— 無いまま進めると仕様書に経緯が溜まる |
| 未決事項の節が仕様書側にある | 手順1の3つ目を飛ばす |
| 版数で git タグを打つ | 手順11・12 を飛ばす |
| タスク台帳が仕様を参照している | **飛ばさない。** 手順7がこのスキルの中心で、ここが抜けると仕様変更が実装に届かない |

## なぜ要るか

仕様書は単独では存在しない。**版数を指すポインタ**(README・AGENTS.md の「現在のステータス」など)と、**下流の成果物**(タスク台帳・決定記録)がぶら下がっている。

とくに**タスク台帳へ追従させない限り、仕様変更は実装に届かない** — 実装ループが読むのは仕様書ではなく台帳の行だから。ここが抜けると、仕様は新しいのに実装は古い決定のまま進む。**エラーも不合格も出ないので、誰も気づかない。**

## 手順

1. **内容変更を確定する**。仕様書に書くのは「何を作るか」だけ。**根拠・却下した案・上書きされた旧記述を仕様書に残さない**(混在すると、grep した実装者が毎回どちらが正かを裁定させられる)。それらの置き場は決定記録側:
   - **決定済み** → 決定記録に本文を書き、仕様書の該当節には**結論だけ**を反映する
   - **未決** → 仕様書の未決事項の節に書く(対応する節がまだ無いため、その項目自体が仕様として働く)
   - **未決が決定に変わった** → 未決の節から決定記録へ移し、結論を該当節に書く。**未決の節に決定内容を残さない**
2. **版を上げる**(版数運用がある場合)。仕様書のタイトル行または冒頭の版数表記を上げる。**セットで版を合わせる文書が複数ある場合は、片方しか実質変更がなくても同じ値に揃える**。
3. **版履歴に1行足す**(版数運用がある場合。置き場は決定記録側)。`版 / 日付 / 追加・改訂された決定番号` だけを書き、**変更内容そのものは書かない**(決定の本文が持つ)。仕様書の冒頭に変更点の説明を書き足さない。
4. **「現在の版を指す」参照箇所を全て更新する**(版数運用がある場合)。所在は都度 grep で確認する — 前回の一覧を信じない。

   ```bash
   grep -rn 'v[0-9]\+\.[0-9]\+' --include='*.md' .
   ```

   典型的な参照元: README、AGENTS.md の「現在のステータス」。**AGENTS.md には版数行だけを更新し、変更点の説明を書かない**(全セッション・全サブエージェントが起動のたびに無条件で読み込むため、履歴を蓄積するとその分だけ毎回の読み込み量が増える)。
5. **書き換えてよい版数と、書き換えてはいけない版数を区別する**(版数運用がある場合)。
   - **更新する** = 「現在の版を教えている文」(`仕様書(現行 vX.Y、正)`)
   - **触らない** = 「いつの出来事だったかを記録している文」(`vX.Y で確定`・`vX.Y で新設`)。git blame のようなもの
6. **セッション依存の表現を掃く**。`grep -rln '本レビュー\|今回の変更\|このセッション' --include='*.md' .` で、後から読むと意味が消える表現を探し、版数や決定番号に置き換える。
7. **タスク台帳へ追従する**(台帳があり、実装が進行中の場合のみ)。変更した節番号と決定番号で台帳を検索し、影響するタスクを列挙してから:
   - **状態が `未着手` のタスク** → **その場で書き換える。** `#### spec` の参照先を新しい構成に合わせ、新しい決定を `#### 内容` / `#### DoD` に織り込む。仕様側に検証可能な規則(算出式・不変条件・上限値)が増えたなら、対応する DoD をテストの対象として書く
   - **完了済み(`- [x]`)・実装中・レビュー中** → **内容を書き換えず**、齟齬の有無を判定して報告する。手戻りが要るなら再実装タスクを起票するかを確認する
   - **どのタスクにも載らない決定** → タスクの新設を検討する。既存タスクの `#### DoD` に畳めるならそちらを優先する
   - **値の正が別ファイルにあるものを台帳へ転記しない**。参照先だけを書く
   - 台帳を書き換えたら、対象タスクIDをコミットメッセージに列挙する
8. ** スキル `self-review` を通す**: 確認を取る前に、この回で書いたもの(仕様書・決定記録・台帳への追記)へ、守るべきと書かれているルールを当てる。**とくに決定記録の本文は、書いた根拠から結論が導けるかを1項目ずつ当てる**(出所・却下した案・採らなかった理由のそれぞれ)
9. **確認を取る**。ここまではすべて作業ツリー上の編集で、git には記録していない。**変更の要約(何をどう変えたか・影響範囲・残課題)を報告し、コミットしてよいか確認する。** 確認なしに commit・tag・push しない — 仕様がまだ動く段階でコミットが先行すると、差し戻しの手間が増える。
10. **コミットする**。変更したファイル一式を1コミットにまとめ、「何を変更し、なぜ版を上げたか」を書く。
11. **タグを打つ**(タグ運用がある場合)。**過去の版のタグが抜けていないかを、リモートを見て確認する** — `git ls-remote --tags origin`。クローンによってはタグを取得しないので、`git tag -l` は「ローカルに無いだけ」を「抜け」と誤判定する。
12. **確認する**(タグ運用がある場合)。`git show vX.Y:<仕様書のパス> | head -1` で、タグ先の内容が意図した版かを見る。

## 注意

- 手順1〜7 は機械的な同期作業で、内容の是非を判断する場面ではない。**内容判断が必要になったら(仕様の矛盾の発見など)手順を中断して報告する**
- **手順9の確認ゲートを飛ばさない。** 手順7までは何度でもやり直せるが、コミット以降は履歴に残る
- 既存タグを `-f` で無条件上書きしない。`git tag vX.Y` が失敗したら原因を確認してから対応する
