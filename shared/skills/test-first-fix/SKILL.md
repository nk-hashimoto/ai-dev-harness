# test-first-fix — 再現テスト先行のバグ修正

**前提**: バグの再現手順が確立していること。原因が分かっていないなら先にスキル `bug-hunt`。

## 手順

1. **バグを再現する最小のテストを書く**。
   - 既存のテスト規約(配置・命名・アサーションの書き方)に合わせる。自分のスタイルを持ち込まない。
   - **振る舞いをテストする**。内部実装の呼び出し回数やプライベート関数ではなく、外から見える結果を書く。
   - テスト名にバグの内容を書く(「〜のとき〜になる」)。issue 番号だけの名前にしない。
2. **実行して red を確認する**。ここを飛ばさない。
   - **green になってしまったら、そのテストはバグを捉えていない。** 再現条件の理解が誤っているので、修正に進まず再現手順の見直しに戻る。
   - red の**失敗メッセージ**も見る。期待と違う理由で落ちている(import エラー、セットアップ漏れ)なら、それはまだ red ではない。
3. **修正を実装する**。テストを通すための最小の変更に留める。テスト側は触らない。
4. **green を確認する**。
5. **周辺の既存テストを全実行する**。修正が別の期待を壊していないか見る。
6. **同型のバグを grep する**。1箇所直したパターンが他にもあれば、同じ形のテストを足して直す(スコープが膨らむなら別タスクとして起票)。

## 注意

- **テストを弱めて green にしない**(P4)。assert の削除・skip の追加・期待値の書き換えは品質報告の偽装と同じ。テスト側を直してよいのは、仕様変更の根拠を引用できるときだけ。
- 修正のついでのリファクタリングを混ぜない。diff に「テスト追加 + 修正」以外が入っていたら分離する。
- 再現テストが書けない種類のバグ(タイミング依存、外部サービス依存、実機固有)は、無理に書かず**書けない理由と代替の検証方法**を報告に明記する。フレーキーなテストを残す方が損。
