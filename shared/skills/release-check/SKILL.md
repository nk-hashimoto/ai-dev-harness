# release-check — 報告の基準の検証

**起動条件**: ユーザーが `/release-check` と明示的に呼んだときだけ。タスクの締めくくりとして自発的に起動しない。

**目的**: 「完了」の主張を、**実行結果**で裏付ける。「たぶん通る」は実行していない証拠。

## 手順

**正は `~/.claude/norms/working-norms.md` の「報告の基準」。** その節を開き、**書かれている項目を上から順に**検証する。各項目に **pass / fail / N-A(理由つき)** を付ける。

**コードを変えているなら、`~/.claude/norms/01-engineering-principles.md` §5-4「コードを変えたときの完了条件」も同じように検証する。** 成果物を問わない条件と、コードに固有の条件が分かれて置いてある。

**項目をこのスキルに書き写さない** — 基準は育つので、書き写すと片方が黙って古くなる。以下は「どう検証するか」だけの補足で、項目そのものではない。

- **動作の確認** — 何をどう確認したか(実行コマンド、テスト、確認した画面)を書けること。書けなければ fail
- **静的検査とテスト** — プロジェクトの実際のコマンドを特定して(ビルド定義と CI 設定)**実行する**。結果を貼らずに要約する(失敗があれば失敗箇所は具体的に)
- **ドキュメントの追随** — 変更したシンボル・仕様用語を doc に grep して確認する
- **diff への責任** — `git diff` を通して見て、意図しない変更・debug 残骸がないこと
- **ルールを自分の出力に当てたか** — `/self-review` を実行済みか。未実行なら fail(このスキルの中で代替しない)

## 出力

- 全項目の pass/fail 表(項目名は正の節から引く)
- fail 項目ごとの**残作業リスト**(何をすれば pass になるか)
- 判定: 全 pass なら「完了」、1つでも fail なら **「残課題つき進捗」**として報告文を組み立てる

## 注意

- **チェックを形骸化させない。** 静的検査とテストは必ず実際にコマンドを走らせる。落ちたら落ちたと書く(P2)。
- テストが落ちているのに「既知の失敗」で pass にしない。既知なら、いつからか・原因は何かを書く。
- このスキルは判定まで。fail の修正は判定を出したうえで別途行う(修正してから判定を書き換えるなら、両方の結果を残す)。
