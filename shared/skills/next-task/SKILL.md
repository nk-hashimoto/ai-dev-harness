# next-task — タスク1件を進める

あなたはオーケストレーター。**実装は原則としてサブエージェントへ委譲する。** 1回の実行で1タスクをレビューへ渡せる状態まで進める。着地はプロジェクトの `WORKFLOW.md` に従い、既定はMR/PR提出まで。**タスク完了は台帳の状態定義に従い、承認・本流への取り込みを確認してから**。

**ツール固有の読み替え**(role の起動・再開の方法、連続実行の方法、台帳の書式が違う場合の対応表)は、使っているツールの runtime adapter(`~/.agent-norms/runtime/<ツール名>.md`)が持つ。着手前に読む。

例外は**小さめの実装**(コメントの訂正、1フィールドの追加など、変更内容が既に確定していて数十行で終わるもの)。委譲の目的は枠の節約なので、サブエージェントのコールドスタートのほうが実装より高くつく規模では自分でやってよい。その場合も検証とレビュー委譲は省かず、**自分で実装したことを手順9の報告に明示する**。

## 手順

0. **土台と状態を照合する**。着手前に `~/.agent-norms/working-norms.md`「着手前(必ずやる)」「セッション運用」を読む。
   - `git status` と `git fetch` で現実を確認する。本流は `docs/dev/mainline-branch` があればそれ、無ければ既定ブランチ。未コミット変更を捨てずに、正の仕様を読む前に本流の更新を確認・取り込む。土台を更新したら自動ロード済みの規範・仕様も読み直す。
   - 台帳の状態・実行記録を読み、退避先は依存IDと移行確認に必要な範囲だけ読む。旧書式なら台帳の移行手順を適用する。状態や依存が不明なタスクは選ばない。
   - 本流の台帳に未反映の作業を取り直さないよう、openなMR/PRのタスクIDと、保存規約に従う作業ブランチ・実行記録も照合する。MR/PR提出前に中断した作業も対象にする。管理情報はタスクID単位で復元し、別タスクの実装差分を取り込まない。
   - 記録されたMR/PRを `WORKFLOW.md` §3で定めた作成・状態照会方法で確認する。**openは完了にしない。未マージでclosedなら要人間確認を付け、再作成・取消しを推測しない。取得失敗時も状態を推測せず、影響するタスクと依存先を保留する。** 独立タスクは進めてよい。
   - マージ済みは、MR/PRのマージ先となる本流ブランチへの取り込み、最新差分に対する必要な承認・検証、DoDと報告の基準を確認する。残件があれば完了にせず要人間確認へ。満たせば `完了` / `[x]` に更新し、本文を保存して退避する。
   - MR/PRを使わないタスクは、`WORKFLOW.md` の完了証跡を確認して同じ完了処理を行う。証跡の定義が無ければ人に確認する。
   - **完了同期の変更は `WORKFLOW.md` の台帳保存方法で共有する。** 未承認の本流pushは行わない。同期用MR/PRが必要なら1件にまとめ、同期だけの変更を実装MR/PRとして再追跡しない。同期が未共有でも、選定時には本流ブランチ・リポジトリサービスの証跡を再確認する。
1. **選定する**。状態・依存・優先順の正はタスク台帳。
   - `#### ⚠要人間確認` があるものは飛ばす。回答が得られたら判断を記録して解除する。
   - このセッションが担当する、または中断が確認でき引き継ぐ `実装中` の再開、または人から明示的な差し戻しがある `レビュー中` のタスクを先に扱う。複数なら台帳の種別・並び順を使う。他の稼働中セッションの作業は取り直さない。担当の稼働状況が不明なら確認する。
   - 再開対象が無ければ、`未着手` かつ `deps` が全て完了しているタスクを台帳の優先順で選ぶ。**ファイルが別でも依存MR/PRが未マージなら着手しない。** 台帳に無いIDを完了とみなさず、退避先も確認する。取消しは完了ではない。
   - 依存が無くても、未マージの別タスクと実装対象ファイルが重なるものは待つ。台帳・決定記録等の共有管理文書だけの重なりは対象外とし、IDごとの追記を保持して取り込み時に照合する。
   - 着手可能なものが無ければ、完了・レビュー待ち・判断待ちを区別して報告し、ループを終了する。承認待ちを空回りで再取得しない。
2. **作業場所を確定する**。
   - 新規タスクのブランチ命名・作業場所は対象ディレクトリの `AGENTS.md`、`WORKFLOW.md`、`IMPLEMENTATION-RULES.md` §1が示すプロジェクト固有の規約文書・決定記録、既存の慣習から特定する。文書の名称や形式はプロジェクトの実態に従い、命名を特定できなければ聞く。未マージの別タスクの変更を土台に積まない。
   - 再開・差し戻しは実行記録のブランチとMR/PRを再利用する。記録とgit・リポジトリサービス上の状態が違えば現実を確認し、新規ブランチや重複MR/PRを作らない。
   - 別ブランチへ移る前に、現在の作業と管理情報を保存規約に従って保存し、未コミット変更を持ち越さない。共有管理文書は古い状態で上書きせず、タスクIDごとの差分を維持する。
   - `実装中` にして、台帳の `実行記録` を更新する。差し戻しコメントと、プロジェクトで定めたAIレビュー記録（無ければ現在タスクのレビュー履歴）を読み、未完の工程から再開する。完了済みの工程は、その前提や成果物が変わった場合だけやり直す。
3. **実装委譲**: 委譲の前に `~/.agent-norms/working-norms.md`「委譲・スコープ・分量」を読む。implementer role を起動し(完了を待つ)、タスクIDと台帳の該当タスク本文、差し戻しなら今回のレビューで要対応と判定された指摘、修正に必要な既存指摘と再開位置を渡す。
   - **role は台帳の実装 tier で選ぶ** — `#### impl` が無い、または `standard` → `implementer`。`advanced` → `implementer-advanced`
   - `#### impl` に対応する role 定義が無い、または値が読めない場合は、**起動せず報告して止まる**(黙って既定へ落とさない)
   - **モデルは role 定義に固定されたものを使う。** 起動時にモデルを上書きしない(エイリアスは解決先が更新で変わるため)。role とモデルの対応・起動方法は runtime adapter が正
   - **差し戻しの起動は、指摘の重さで決める。**

     | 差し戻し | 起動 |
     |---|---|
     | 重大指摘・1回目 | `implementer-advanced` を新規起動する(昇格。手順5) |
     | 重大指摘・2回目以降 | 前回の `implementer-advanced` を再開する |
     | 軽微指摘だけ(自分で直さないと決めたとき) | 前回の implementer を再開する(昇格しない) |

     - 再開できるかどうか(同じエージェントを続ける手段があるか、キャッシュが残っている時間内か)は runtime adapter の条件に従う。再開できなければ同じ role を新規起動する
     - 再開でも渡すものは新規起動と同じ(指摘の番号・内容・判定・未解消回数)。変わるのは受け手の読み直しの範囲だけ
4. **検証を自分で実行する**。実装担当の「通りました」という報告は、**自分が実行したことにはならない**。
   - **検証コマンドはリポジトリから特定する** — ビルド定義(`Makefile` / `package.json` / `pyproject.toml` / `build.gradle` など、その言語のもの)と CI 設定を読み、そのサブシステムで実際に使われているものを使う。**このスキルにコマンドを埋めない**
   - 最低限、**そのプロジェクトの静的検査(型チェック・Lint など、あるものだけ)とテスト**を通す。**そのタスクの DoD が名指しした検証があれば、それも自分で回す**
   - **実行環境・設定・ビルド構成で分かれる仕様は、分岐の両方で回す。** テストが書かれていても、その回で実行されなければ踏まれない — **緑であることは踏んだ証拠にならない**。片側しか回せなかったら「未検証」と報告に書き、行き先タスクへ申し送る
   - **「テストが通ったか」ではなく「このタスクが実装した決定を、どのテストが踏んだか」で見る。** 仕様の場合分けを列挙し、それぞれに対応するテストの行を指せること。指せないものは未検証。とくに**既定へ委譲する分岐**(ハンドラが false を返して既定に任せる等)は、その分岐が壊れていても結果が同じになるので、区別できるケースが別に要る
   - 検証結果を見る前に、**それが自分の変更後のビルドの結果か**を確かめる(キャッシュ・古い成果物・再起動していないプロセスは平然と旧版の結果を返す)
5. **レビュー委譲**: 初回・再レビューとも、渡す前にスキル `self-review` を実行する。
   reviewer role を**実装の文脈を渡さない新しいコンテキスト**で起動する(完了を待つ)。レビュー担当は指摘を**重大 / 軽微**に分類し、各指摘に通し番号(`R1` `R2` …)を振って返す。**差し戻し後も残っている指摘は同じ番号で再掲される** — 同じレビューラリーで、どれが直ってどれが残っているかを追えるようにするため。

   - **再レビューは前回の reviewer を再開する。** 依頼に書くのは ①前回 HEAD からの差分の範囲(`git diff <前回HEAD>..HEAD`)②implementer の対応の要約 ③新たに見てほしい点。reviewer 側の読み方は reviewer role の「再レビュー」が正
     - 再開できないとき(手段が無い・runtime adapter の条件を外れた)は新規起動し、前ラウンドまでの指摘一覧(番号・内容・判定・未解消回数)を添える
   - 指摘の行き先(現タスクで直す / 申し送り / 起票)を判定する前に `~/.agent-norms/working-norms.md`「レビュー指摘の行き先」を読む

   各レビュー後、プロジェクトで定めたAIレビュー記録の保存先があれば、全指摘のID・未解消回数・修正と判定の要点をそこへ残す。保存先が無ければ、現在タスクのレビュー履歴を使う。AIレビューで解消した指摘をMR/PRへ移すことは前提にしない。

   **重大が無ければ、レビューはそこで終了**。
   - 軽微のうち「現タスクで直す」と判定されたものは、**再委譲せず自分で直す** — 数行の修正にサブエージェントのコールドスタートを払うのは割に合わない
   - **自分で直したら、手順4の検証をもう一度通す。** ここを飛ばすと、自分の修正だけが誰にも検証されないまま MR に入る
   - 自分で直した内容は手順9の報告に明示する(diff に出るので隠さない)

   **重大があれば、同じタスクのimplementerへ差し戻す。打ち切りは指摘単位で数える。** 差し戻し時は、今回のレビューで要対応と判定された重大指摘を渡し、過去の指摘は修正に必要な範囲だけ添える。軽微指摘は手順5の行き先判定に従う。
   - 初出をその指摘の1回目とし、修正後のレビューでも未解消なら2回目、3回目と数える。**同じ指摘が3回目のレビューでも解消していないとき**、そのタスクに `#### ⚠要人間確認` を付ける。総レビュー回数では打ち切らない。
   - 新しい根拠ある指摘は新IDの1回目から数える。同じ原因・観点の言い換え、再発、セッション再開ではID・回数をリセットしない。プロジェクトで定めたAIレビュー記録（無ければ現在タスクのレビュー履歴）をreviewerへ渡す。人の判断で再開するときは、継続する方針と再相談の条件を記録し、それに従う。
   - 重大指摘による最初の差し戻し以降は、次の実装起動から `implementer-advanced` へ昇格させる(手順3の表)。`implementer-advanced` の定義が無い導入では同じ定義を使う。**軽微指摘だけの手戻りは昇格させない。**
   - コード修正後は手順4の検証を行う。
   - 打ち切り時は、①残る指摘、②試した修正と結果、③人に決めてほしいことを台帳に書く。状態は `実装中` のまま保持する。
   - `#### ⚠要人間確認` を付けて停止した場合に限り、このタスクを保留して独立した別タスクへ進んでよい。停止していないレビューラリー中は、別タスクを開始せずこのタスクを継続する。
   - 新しい有効な指摘を解消している間は継続する。修正が互いを打ち消す場合は同じ問題の再発として扱う。コマンド実行等の失敗への再考・相談はnormsの規則を適用する。

6. **提出準備**:
   - **提出ゲート**: **2つの基準を1件ずつ当てる** — ①**タスクの完了条件**(台帳の `#### DoD`。成果物の検証はここで満たし、人の承認・取り込みは提出後に確認する)と ②**報告の基準**(`~/.agent-norms/working-norms.md`「報告の基準」。*完了と報告してよいか*の条件)。**別物なので片方では代替できない**
   - 実装担当の報告にある自律決定を決定記録へ追記する
   - **実装担当・レビュー担当の報告にある「提案」「申し送り」「未決」を1件ずつ着地させる。** 行き先は現タスクの修正か、台帳への追記。**報告に書かれただけのものは消える** — 会話は残らず、次のセッションが読むのは台帳と git だけ。着地させないと決めたなら、その判断を報告に書く
   - **申し送りの書式**: **行き先は未着手タスクに限る**(完了済みタスクに書き足しても誰も読まない。該当が無ければ新設する)。その `#### 内容` か `#### DoD` に1行足し、**行末に出所ラベル `(出所: <元タスクID> レビュー)` を必ず付ける** — 着手時に「この行はどこから来たのか」を辿れるようにし、`grep '出所:'` で残っている申し送りを一覧できるようにするため
   - **新規タスクを起こす条件**: **まず起こさずに済まないかを見る**(既定の行き先は現タスク)。送ると決まったら、①既存タスクの `#### 内容` / `#### DoD` に1行足すのが第一選択 ②どの既存タスクにも属さないものだけ新設する ③複数の申し送りはまとめて1タスクにしてよい。**タスクを細かく割らない** — 論理変更の単位で起こしていくと台帳が際限なく膨らむ
   - **仕様の側を直す必要が出たら、このループでは直さずスキル `spec-change` へ回す**(版数を指す参照箇所と台帳への追従が要るので、コミット1つでは閉じない)
   - 台帳は `[ ]` のまま維持し、実行記録に検証の所在と、プロジェクトで定めたAIレビュー記録があればその所在、次の操作を残す。合格基準の変更が必要なら人に提案し、実装者の判断でDoDや期待結果を緩めない。

7. **セルフレビュー**: スキル `self-review` を実行する。**呼ばれるのを待たない。** 作った成果物の種類から読み返すルールが決まるので、それを自分の出力に当てる。指摘が出たら直してから次へ進む。
   - hooksを前提にしない。検証とレビューで、実行結果と文書・差分の妥当性を確かめる。
   - 実装担当が書いた分だけでなく、**手順5で自分が直した分と、手順6で自分が書いた台帳・決定記録の文章も対象**

8. **提出する**。
   - **1論理変更 = 1コミット**で作成する。初回提出でも無関係な変更を1コミットにまとめず、差し戻し対応もこの原則とプロジェクトのレビュー運用に従う。
   - **着地の仕方をこのスキルに埋めない** — 手順2(ブランチ命名)と同じ要領で、プロジェクトの規約(開発ワークフロー文書・`IMPLEMENTATION-RULES.md` §1が示す規約文書・決定記録)から読み取って**そちらに従う**。マージまでを規約が定めているならマージまで行う
   - **読み取れなければ「push して MR/PR を作り、止まる」**(既定)。不可逆な操作を含まない側に倒してあり、マージが要るなら後から足せる。テンプレートがあればそれに沿って埋める(テンプレートの所在も規則も、同じくリポジトリから読み取る)
   - **レビュー担当の合格は、マージの承認ではない。** 人のレビューへ出せる状態になったことの判定でしかない。規約がマージまで含んでいる場合、マージしてよい根拠はその規約であって、合格判定ではない
   - MR/PR本文またはコメントに、`WORKFLOW.md` §7のレビュー証跡を残す。差し戻し後は最終差分に必要な検証を更新し、人のインタビューで決まった事項も記録する。
   - 作成・更新に成功したら `レビュー中` とMR/PR URLを記録し、台帳の保存方法に従って共有する。提出後に管理情報だけを更新する場合は、実装差分が無いことを確認する。実装差分を変更した場合のみ、影響する検証を再実行する。提出に失敗したら `実装中` を維持する。再実行前に既存MR/PRを検索し、重複作成を防ぐ。
   - MR/PRを使わないタスクや、規約によりマージまで実行した場合も、手順0の条件を確認してから完了にする。連続実行するときも、次の選定は手順0から行う。
9. **報告**: タスクID・状態・要点・MR/PR・検証記録への参照・次のタスクまたは停止理由を簡潔に報告する。「提出済み」と「完了」を区別する。AIレビュー記録を設けない場合は、指摘ごとの `ID / 指摘の要点 / 判定 / 未解消回数 / 修正結果` を短い表で直接報告する。これはMR/PRへの記載を求めるものではない。

## 中断と再開

手順の区切りで台帳の実行記録を更新し、プロジェクトで定めたAIレビュー記録があればそこも更新する。終了・中断の指示を受けたら新規タスクを開始せず、未コミット変更の意図と次の操作を保存する。詳しい引き継ぎが必要ならスキル `handoff` を使い、台帳にはその参照を置く。突然終了して記録が古い場合も、再開は手順0でgit・MR/PRと照合してから行う。稼働中の別セッションを引き継いだと推測しない。

## 注意

- 判断に迷ったらプロジェクトのワークフロー文書(エスカレーション規則・事前に決めた実装詳細)に従う
- 台帳の書式を壊さない。タスクの削除禁止
- 1実行1タスク。まとめて複数消化しない(レビュー粒度を保つため)
