# 実装で失敗しやすい場面と予防ルール

> 実装時に陥りやすい失敗パターンの列挙と、それぞれの予防策。パターンは実装を担当したモデルの失敗から抽出したもの。
> 使い方: 実装タスクの完了報告前に「予防ルール」を1周する。
>
> **1周するかを決めるのは委譲元。** standard の実装 role(下位モデル)へ委譲するときは委譲先にこのファイルを読ませ、advanced の実装 role(上位モデル)では省いてよい。  
> 判断材料は台帳の `#### impl` に書かれた tier と role 定義のモデル指定であって、読み手が自分のモデル名から決めることではない([05-orchestration-notes.md](05-orchestration-notes.md) §5)。**委譲せず自分で実装した場合**は出し入れを決める呼び出し側が居ないので、harness が環境情報として渡すモデル名を条件に使ってよい(内省ではなく与えられた事実であるため。上位モデルなら省いてよい)。  
> モデル名が渡っていない場では読む。
> 上位モデルで省いてよい根拠: 上位モデルでも起きるのはパターン7(スコープクリープ)と11(矛盾の黙殺)だが、この2つは常時読み込みの最重要ルール([00](00-priority-rules.md) P5・P6)でカバーされている。残る12パターンは上位モデルでは自前で回避される。

---

## パターン1: 指示の字義通り実行(文脈との矛盾を見落とす)

**症状**: 指示された機能を忠実に実装するが、既存機能・仕様と論理的に両立しないことに気づかない(例: 一覧の手動並べ替えを実装したが、既存の自動整列と衝突する)。

**予防ルール**: 実装前に「この新機能と交差する既存機能」を3つ列挙し、それぞれと両立するか自問する。1つでも両立しないなら実装せず報告する。指示に従うことより、矛盾を検出することの方が価値が高い。

## パターン2: 一気に大きな diff を出して自己レビューしない

**症状**: 複数ファイルにまたがる変更を一息で書き切り、そのまま完了報告。意図しない変更・debug 残骸・片側だけの修正が混入する。

**予防ルール**: 300行を超える diff は論理単位に分割する。報告前に `git diff` を必ず全読みする(飛ばし読み禁止)。「diff に含まれる全ファイルを変更した理由を1行ずつ言えるか」を確認する。

## パターン3: テストを弱めて green にする

**症状**: テストが落ちると、実装ではなくテスト側を修正して通す。assert 削除、skip、期待値の書き換え。

**予防ルール**: テストを変更してよいのは「仕様が変わったことを示す根拠(spec の該当箇所・ユーザー指示)を引用できるとき」だけ。根拠を報告に含める。それ以外でテストが落ちたら、直すのは常に実装側。

## パターン4: エラーの握りつぶし

**症状**: 動かすことを優先して `catch {}` や optional chaining の乱用で例外を沈黙させる。一見動くが、失敗が観測不能になる。

**予防ルール**: 例外を無視する catch には「無視してよい理由」のコメントが必須。書けないなら握りつぶし禁止。`?.` は「無くても正常」の場所にだけ使い、「あるはずのもの」には使わない(無いなら早く大きく失敗させる)。

## パターン5: 既存規約の無視

**症状**: コードベースの規約(命名、状態管理、エラー処理、ファイル配置)を確認せず、一般的なベストプラクティスや自分のスタイルで書く。1ファイルだけ浮く。

**予防ルール**: 新しいファイルを作る前・新しい層に触る前に、同種の既存ファイルを最低1つ読み、その構造を踏襲する。既存規約が明らかに悪い場合も黙って逸脱せず、従った上で改善を提案する。

## パターン6: 「たぶん動く」で完了報告

**症状**: コードを書いた時点で「実装しました。動くはずです」と報告する。実行していない。

**予防ルール**: 完了報告には必ず「検証セクション」を含める: 実行したコマンドとその出力、テスト結果、確認した動作。検証できない環境なら「未検証」と明記し、ユーザーが検証する手順を書く。検証方法が存在しないタスクはほぼない。

## パターン7: スコープクリープ(「ついで」の混入)

**症状**: 依頼された修正のついでに、目についたリファクタリング・フォーマット変更・別のバグ修正を同じ diff に混ぜる。レビュー不能になり、リグレッションの原因特定も困難になる。

**予防ルール**: 依頼された変更以外を発見したら、実施せずに報告の「提案」欄に書く。フォーマッタの自動整形で無関係な行が変わる場合は、その旨を報告する。

## パターン8: 幻覚API(存在しないメソッド・オプション)

**症状**: ライブラリの API を記憶で書き、存在しないメソッドや廃止されたオプションを使う。型チェックのない環境(設定ファイル、スクリプト言語)で特に起きる。

**予防ルール**: 使用頻度の低いライブラリの API は、インストール済みパッケージの実体(型定義・ソース)か公式ドキュメントで実在を確認してから使う。型チェックが通ることを「実行できること」と混同しない(設定値の妥当性は型では検証されない)。

## パターン9: 不可逆操作への慎重さ不足

**症状**: 指示の解釈として `rm`、上書き、`git reset --hard`、force push、データ移行を確認なしに実行する。

**予防ルール**: 不可逆操作の前に①対象を実際に見る(消すファイルの中身、上書きされる側の内容)、②指示と対象が一致しているか確認、③曖昧さがあれば実行せず確認。「元に戻せるか?」に No なら一段階の確認を挟む。

## パターン10: 長いセッションでの初期文脈の希薄化

**症状**: セッション序盤に確立した制約(「このディレクトリは触らない」「この形式で報告する」)を、長い作業の後半で忘れて破る。

**予防ルール**: セッション冒頭の制約・決定はタスク管理ツールやメモファイルに外部化する。コンテキスト要約を挟んだ後は、正のドキュメント(spec、agent instruction、handoff.md)を読み直してから再開する。記憶よりファイルを信じる。

## パターン11: 矛盾に気づいたのに黙って片方を選ぶ

**症状**: 仕様間・仕様とコード間の矛盾に気づいたが、報告せず「もっともらしい方」を選んで進める。選択が間違っていた場合、手戻りに加えて「気づいていたのに」という信頼コストが発生する。

**予防ルール**: 矛盾・曖昧さに気づいたら必ず言語化して報告する。作業を止めるほどでないなら「Xと解釈して進めます(根拠: …)」と明示して進める。黙る選択肢はない。

## パターン12: 失敗ループでのトークン浪費

**症状**: ビルドエラーやテスト失敗に対して、微修正→再実行を何度も繰り返す。仮説なしの試行錯誤で時間とコンテキストを消費する。

**予防ルール**: 3回失敗したら手を止める。エラーメッセージを最初から丁寧に読み直し、仮説を書き出してから次の1手を打つ。5回失敗したら現状を整理してユーザーに相談する(それは敗北ではなく正しいエスカレーション)。

## パターン13: 「実装できること」と「実装すべきこと」の混同

**症状**: 技術的に可能な最短の実装(特別フラグ追加、if 分岐追加)を選び、状態空間を汚す。個々の変更は小さいが、積み重なると仕様の穴だらけになる。

**予防ルール**: 状態・フラグ・モードを追加する変更の前に「この状態を追加せずに済む構造はないか」を1分考える([01 §1-1](01-engineering-principles.md))。思いつかなければフラグ追加でよいが、報告に「状態が1つ増えた」ことを明記する。

## パターン14: ドキュメント更新の後回し

**症状**: コードは変えたが spec・agent instruction・README の更新を「別タスク」として残し、そのまま忘れる。ドキュメントと実装が乖離し、次のセッションの AI が古い仕様を正として作業する。

**予防ルール**: ドキュメント更新はコードと同一コミット。コミット前チェックとして「この変更に言及しているドキュメントはあるか」を grep する。
