# 上位モデルに作業させるときの指示の書き方(呼び出し側向け)

> **これは呼び出し側が読む資料。** 委譲プロンプト・サブエージェント定義・Skill・この規範自体を書く/直すときに開く。  
> ここにあるのは**何を書くか**で、サブエージェント定義の**器**(置き場所・書式)は runtime adapter(`runtime/<ツール名>.md`)の「role 定義」、Skill の命名・起動条件の決め方は [skill-design.md](skill-design.md)。
> **委譲一般はここに書かない。** 何を委譲するか・渡す4点・委譲結果のレビューは、読み手が同じ「呼び出し側」なので引き寄せられるが主題が違う。  
> 正は [02-thought-processes.md](02-thought-processes.md) §7 と [working-norms.md](working-norms.md)「委譲・スコープ・分量」。  
> ここの主題は**モデル階層を意識した指示の書き方**なので、モデルに依らない規則でも主題が合えば置いてよい(§5・§6)。
> **実行側は読む必要がない** — 実行側向けの調整は「余分な検証指示を書かないこと」で実装済みで、指示の不在は誰が読んでも等しく効くため(→ §5)。だから実行中に自分のモデル名を根拠にこのファイルを開く判断は要らない。
>
> **賞味期限**: §1〜§4 は上位モデル(執筆時点では Claude Opus 5 系)の性質から導いたものなので、割り当てるモデルを変えたら**出典を読み直して更新する**。§5・§6 はモデルに依らない設計ルールなので残る。  
> 「上位モデル」「下位モデル」が具体的にどのモデルを指すかは、runtime adapter(`runtime/<ツール名>.md`)の役割表が正。モデルごとの差分(effort の目盛り・推論の扱い)も adapter が持つ。**3役すべてに同じモデルを割り当てている場合、この資料の §1〜§4 はそのモデルが上位モデルに当たるときだけ効く。**
>
> 3役(オーケストレーター / 実装 / レビュー)のどれを上位モデルで回すかは運用で変わる。上位モデルは下位モデル向けのプロンプトでもそのまま動くが、**過剰検証・スコープ拡大・冗長さ**の3点だけは指示側を調整しないと逆効果になる。
> 出典は、上位モデルに割り当てたモデルの公式プロンプトガイド(所在は各 runtime adapter)。

## 1. 上位モデルに書いてはいけない指示(書くと悪化する)

| 書きがちな指示 | 上位モデルで起きること |
|---|---|
| 「非自明なタスクには最終検証ステップを入れる」「検証用にサブエージェントを立てる」 | 自前の検証と二重になり、品質が上がらないままトークンを消費する |
| 「もう一度確認してから答える」「回答前に再検証する」 | 同上。自己修正は指示なしで行われる |
| レビューで「重大なものだけ報告して」「保守的に判断して」 | 字義通り従って**報告件数が減る**。上位モデルのレビューは誤検知が少ないので、**全部出させて別パスで絞る**方が取りこぼしがない |
| 「考えるな」「推論を出すな」系の抑制 | thinking 無効時に内部タグが漏れやすくなる。thinking は切らず effort で絞る |

**外す対象は「開放的・重複的な検証」に限る。** 一手で終わる具体作業(報告前に diff を通して見る、ベースラインのテスト実行)は残す  
— これらは上位モデルなら指示がなくてもやる作業なので明記コストがほぼ無く、一方で**同じ文書を下位モデルも読む**ため、緩めると P2・P4(未検証で完了と言わない / テストを弱めない)の担保が消える。  
緩めて得られるトークンより、下位モデルが「diff を見ずに混入なしと書ける」余地の方が高くつく。

**この資料側での対応(済)**: P7 の見出しを「diff を全読みする手順」から「diff 全体に責任を持つ」に変更(ただし**通し読みの一手は必須のまま**)、[03-implementation-pitfalls.md](03-implementation-pitfalls.md) の全周チェックは**委譲元が出し入れする**(上位モデルに実装させるときは省いてよい。委譲がなく自分で実装する場合は読む)。  
出し入れの判断が呼び出し側にあり、`model:` に書かれた事実で決まるので §5 と両立する。

## 2. 上位モデルに書くと効く指示

- **スコープ固定**: 上位モデルは頼まれていない工程を足す・自分の判断でタスクを再定義する傾向がある。「依頼されたスコープが成果物。狭めず広げず別物にすり替えない。前提が間違っていると思ったら1文指摘してから依頼どおり完遂する」を明示する
- **委譲の上限**: 委譲を好むので、小さい仕事にも subagent を立てて時間とコストが増える。「大きく独立した並列可能な仕事だけ・自分の検証には使わない・1体で足りるなら1体」を明示する。「下位モデルへ委譲して使用枠を節約する」というプロジェクト側の方針がある場合は、**上限つきで**適用する
- **長さの校正(宛先で変える)**: 会話の応答・ディスクに書くドキュメントの両方が長くなりやすい。ただし一律に短くさせない — **エージェント間の報告は長くてよい**(オーケストレーターの判断材料であり、事実を削る方が高くつく)。
  - ここで指定して効くのは「生ログを貼らず要約する」だけ。**校正が必要なのはユーザー向けの文章とディスクに書く成果物**で、「結論から書く。埋め草の節・重複する要約を足さない」を明示する(「常設ドキュメントに作業ログを混ぜない」と同じ方向)
- **進捗ナレーションの形**: 「最初のツール呼び出し前に1文で何をするか言う → 作業中は重要な発見・方向転換のときだけ短く → 最後は結論から書く」のように**形を指定する**。禁止形より、望む形を例示する方が効く
- **訂正ナレーションの抑制**: ユーザーの判断・コード・結論が変わる誤りだけ訂正を述べ、影響のない言い直しは黙って直す

## 3. タスクの渡し方(呼び出し側)

- **完全な仕様を最初に一度で渡し、走らせる。** 上位モデルは長時間の自律作業でスタブや置き換え待ちを残さず完遂する側に強い。手順を小刻みに刻んで逐次指示するより、ゴール・制約・受け入れ条件・**やらないこと**を先に全部渡す方が結果が良い
- 委譲時に渡す4点([02 §7](02-thought-processes.md))は変わらない: 完了条件 / 変更してよい範囲 / **変更してはいけない範囲** / 検証方法。上位モデル相手では3番目の重みが上がる(スコープ拡大の抑制になる)
- **effort(推論量の設定)**: 品質が落ちない範囲で下げるのが主要なコスト制御。**考える量を減らしたいときは指示文ではなく effort を下げる**(指示文より確実に効く)。thinking は切らない(切るより低い effort + thinking の方が同コストで良い)
  - 既定値と目盛りはモデルごとに違う。同じ値を別のモデルへそのまま持ち込まない(値は runtime adapter の役割表)
- **無人運転・委譲先の途中停止**: 長い作業の途中で、進捗を報告する文章だけでターンを終えることがある。**文章だけのターン終了を「完了」と読まない**
  - 作業項目は台帳・ToDo・ファイルに置き、未了の項目が残っていて妨げも書かれていなければ、項目を名指しして続行を促す1通を送る。同じタスクで2〜3回続けても進まなければ、本当に詰まっているので止めて見る
  - 走行中のバックグラウンド処理やサブエージェントが残っているうちは完了と扱わない
  - 無人運転の起動プロンプトに、避けたい止まり方(次の手を宣言して終わる・続けてよいか尋ねる・妨げにならない決定を並べて待つ・区切りがよいので報告する)と、**止まってよい場合**(ユーザーの入力なしには進めない・意図的に保護されたものに阻まれた)を名指しで書くと減る。ただし不可逆な操作の確認は外さない。人が応答する対話では書かない
- レビュー依頼は「全件報告 → 別パスで重要度で絞る」の2段に分ける(§1 の3行目)

## 4. 下位モデル実行時との使い分け

| | 下位モデルが実装 | 上位モデルが実装・レビュー |
|---|---|---|
| [03-implementation-pitfalls.md](03-implementation-pitfalls.md) の全周自己チェック | 委譲先に読ませる | 省いてよい(7スコープクリープ・11矛盾の黙殺は常時読み込みの最重要ルール P5・P6 でカバー済み)。委譲せず自分で実装する場合は環境情報のモデル名で判断してよい |
| 手順の細分化 | 有効 | 不要。ゴールと制約を一度に渡す |
| 検証ステップの明示 | 有効 | 書かない(自前で行う)。要るのは**報告に何を含めるか**の指定だけ |
| 主に注意する失敗 | 規約無視・未検証完了報告・幻覚API | スコープ拡大・過剰委譲・ユーザー向け文章と成果物の冗長さ |

この表は**呼ばせる側(オーケストレーター)の判断表**であって、実行側に「自分がどちらか判定して選べ」と渡すものではない(理由は §5)。

## 5. モデルの自己申告に依存する分岐を、常時読み込むドキュメントに置かない

**この資料の適用範囲は、読み手が自分のモデル名を判定して決める設計にしない。** 理由は2つ:

- モデルは自分が何であるかを**内省では知らない**。分かるのは harness が環境情報として渡している場合だけで、渡らない場では、自分を古いモデルと誤認するのが普通。訓練データは自身のリリース前で止まっているため
- 誤認の被害が非対称。「上位モデルなら検証を省いてよい」という条件文は、下位モデルが自分を上位と読んだ瞬間に P2・P4(未検証で完了と言わない・テストを弱めない)を無効化する。逆向きの誤認(上位モデルが余分に確認する)はトークンを損するだけで済む

したがって、どの role・どのモデルも読む [00-priority-rules.md](00-priority-rules.md) と [working-norms.md](working-norms.md) には、**どのモデルが読んでも安全な形**しか書かない: 手順の強制は外す（「diff を必ず全読み」→「diff 全体に責任を持てる状態でなければ報告しない」）が、**検証を省く許可は書かない**。  
「二重検証を自分に課さない」のような上位モデル向けのチューニングは、必要時にだけ開くこのファイルに置く。

適用範囲を決めるのは読み手ではなく**呼び出し側**: agent instruction の参照条件、オーケストレーターが委譲時に渡す指示、サブエージェント定義の `model:` — この3つで決める。

**階層で出し入れしてよい条件**: ①判断主体が呼び出し側にあり(委譲元の指示・エージェント定義・起動パラメータ)、かつ②`model:` / 台帳の `#### impl` のような**書かれた事実**で決まる  
— この2つが揃うときだけ、モデル階層で内容を出し入れしてよい(例: 03 の全周チェックを上位モデルへの委譲では渡さない)。逆に、読み手が自分の名前を根拠に出し入れする形は不可。  
判断主体が明示されていれば、条件文にモデル階層が出てきても問題ない(「委譲元は上位モデルのとき省く」は呼び出し側の指示であって、読み手の自己判定ではない)。**呼び出し側が居ない場合(委譲されず自分で実装する)は、harness が環境情報として渡すモデル名を条件に使ってよい**  
— 内省ではなく与えられた事実だから。渡っていない場では安全側=実施するに倒す。なお呼び出し側が居るなら、そちらの判断(`model:` の値)の方が確実なので、実行側の自己判定に切り替えない。

参照条件そのものも**タスクの形**で書く(「〜を書く/直すとき」「完了報告の前」)。「上位モデルのときは読む」のようにモデル階層を条件に書くと、入口で同じ自己判定を要求してしまう。ただし harness が環境情報としてモデル名を渡している場では、それは内省ではなく与えられた事実なので、条件に使ってよい。

## 6. コーディングエージェント本体との重複に注意

上位モデルを載せたコーディングエージェントのシステムプロンプトは、スコープ固定・訂正の抑制・委譲の抑制について既に同趣旨の指示を持っている。**同じ内容をこの資料側で重ねて強化しない** — 強調の上塗りは、スコープを過度に狭める・報告を削りすぎるといった逆方向の副作用を生む。ここに書くのは「エージェント本体が持っていない前提」(プロジェクト固有の委譲方針との整合、レビューの2段化)に限る。
