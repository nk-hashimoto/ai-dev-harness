# next-task — タスク1件を完結させる

あなたはオーケストレーター。**実装は原則としてサブエージェントへ委譲する。** 1回の実行で1タスクを完結させ、**MR/PR を作った時点で止まる**(マージは人が行う)。

例外は**小さめの実装**(コメントの訂正、1フィールドの追加など、変更内容が既に確定していて数十行で終わるもの)。委譲の目的は枠の節約なので、サブエージェントのコールドスタートのほうが実装より高くつく規模では自分でやってよい。その場合も検証とレビュー委譲は省かず、**自分で実装したことを手順9の報告に明示する**。

## 手順

0. **土台の新しさを確かめる**。`git fetch` して、現在のブランチが本流から遅れていないかを見る。本流ブランチ名は `.claude/mainline-branch`(1行)があればそれ、無ければ既定ブランチ。**遅れていたら、正のドキュメントを読む前に取り込む** — 古い版を正だと思って書いた変更は、マージのたびに衝突するか黙って上書きされる。
1. **選定**: タスク台帳を読み、`- [ ]` のうち `#### deps` の全タスクが `- [x]` の最初のタスクを選ぶ。
   - **`#### ⚠要人間確認` の節があるタスクは飛ばす。** 人の判断を待っている状態なので、取り直しても同じところで止まる(飛ばさないと `/loop` が同じタスクを無限に取り続ける)。飛ばしたタスクIDは手順9の報告に列挙する
   - 該当なし(全完了 or 全ブロック中 or 残りが全て `#### ⚠要人間確認`)なら、状況を報告して終了。`/loop` 実行中ならループを終了する
   - タスクが「人の判断待ち」「実機検証待ち」を含む場合: 手順書・依頼文の作成までを行い、後続の並行可能タスクがあればそちらを選ぶ
2. **ブランチを用意する**。**命名規則をこのスキルに埋めない** — 作業対象ディレクトリを起点に、そのディレクトリの `CLAUDE.md`、リポジトリの貢献ガイド、既存ブランチの命名を見て従う。**どれからも読み取れなければ、推測せず止まって聞く。**
3. **実装委譲**: Agent ツールで実装担当のサブエージェントを起動し(`run_in_background: false`)、タスクIDと台帳の該当タスク本文を渡す。
   - **実装モデルは `subagent_type` で選ぶ。`model` パラメータは使わない** — Agent ツールの `model` はエイリアスしか受け付けず、意図しない世代に解決される。フルモデルIDを固定できるのはエージェント定義の `model:` frontmatter だけなので、**モデルの数だけ定義を用意して型を選ぶ**
   - `#### impl` の節があるタスク → そこに書かれたモデルIDを `model:` に持つ定義を選ぶ
   - `#### impl` が無いタスク → 既定の実装エージェント
   - `#### impl` に値が書かれていて対応する定義がない場合は、**起動せず報告して止まる**(黙って既定へ落とさない)
4. **検証を自分で実行する**。実装担当の「通りました」という報告は、**自分が実行したことにはならない**。
   - **検証コマンドはリポジトリから特定する** — ビルド定義(`Makefile` / `package.json` / `pyproject.toml` / `build.gradle` など、その言語のもの)と CI 設定を読み、そのサブシステムで実際に使われているものを使う。**このスキルにコマンドを埋めない**
   - 最低限、**そのプロジェクトの静的検査(型チェック・Lint など、あるものだけ)とテスト**を通す。**そのタスクの DoD が名指しした検証があれば、それも自分で回す**
   - **実行環境・設定・ビルド構成で分かれる仕様は、分岐の両方で回す。** テストが書かれていても、その回で実行されなければ踏まれない — **緑であることは踏んだ証拠にならない**。片側しか回せなかったら「未検証」と報告に書き、行き先タスクへ申し送る
   - **「テストが通ったか」ではなく「このタスクが実装した決定を、どのテストが踏んだか」で見る。** 仕様の場合分けを列挙し、それぞれに対応するテストの行を指せること。指せないものは未検証。とくに**既定へ委譲する分岐**(ハンドラが false を返して既定に任せる等)は、その分岐が壊れていても結果が同じになるので、区別できるケースが別に要る
   - 検証結果を見る前に、**それが自分の変更後のビルドの結果か**を確かめる(キャッシュ・古い成果物・再起動していないプロセスは平然と旧版の結果を返す)
5. **レビュー委譲**: Agent ツールでレビュー担当のサブエージェントを起動(`run_in_background: false`)。レビュー担当は指摘を**重大 / 軽微**に分類し、各指摘に通し番号(`R1` `R2` …)を振って返す。**差し戻し後も残っている指摘は同じ番号で再掲される** — 人が MR を見たときに「どれが直ってどれが残っているか」を追えるようにするため。

   **重大が無ければ、レビューはそこで終了**。
   - 軽微のうち「現タスクで直す」と判定されたものは、**再委譲せず自分で直す** — 数行の修正にサブエージェントのコールドスタートを払うのは割に合わない
   - **自分で直したら、手順4の検証をもう一度通す。** ここを飛ばすと、自分の修正だけが誰にも検証されないまま MR に入る
   - 自分で直した内容は手順9の報告に明示する(diff に出るので隠さない)

   **重大があれば差し戻す**(最大2往復)。
   - 指摘を添えて実装担当を再起動する
   - **2回目の差し戻し(= 3回目の実装起動)は昇格させる**: `#### impl` の有無に関わらず、**上位モデルの実装エージェント定義があればそれで**起動する。人へのエスカレーション直前の最後の1回に判断力を当てるため。**定義が無ければ昇格せず同じ定義で実行する**(黙って別のモデルに落とさない)。昇格して合格したら手順9の報告に明記する(その系統に `#### impl` を常設すべきかの判断材料になる)
   - **3回目でも不合格なら、人へエスカレーションする**。台帳の該当タスクに `#### ⚠要人間確認` の節を足し(チェックは `- [ ]` のまま)、そこに次の3点を書く。**会話には残らないので、台帳に書かないと消える**
     1. **何が解決していないか** — 残っている重大指摘の番号と内容
     2. **何を試したか** — 3回のラウンドでそれぞれ何を変えたか(同じ手を再試行させないため)
     3. **人に決めてほしいこと** — 判断の分かれ目。分かるなら候補案も添える
   - エスカレーションしたらそのタスクは終了。**他に着手可能なタスクがあれば報告のうえ次へ進んでよい**(1件の停止で全体を止めない)

6. **着地処理**:
   - **完了ゲート**: 台帳を `[x]` にする前に、**2つの基準を1件ずつ当てる** — ①**タスクの完了条件**(台帳の `#### DoD`。*成果物*が満たすべき条件)と ②**報告の基準**(`norms/working-norms.md`。*完了と報告してよいか*の条件)。**別物なので片方では代替できない**
   - 実装担当の報告にある自律決定を決定記録へ追記する
   - **実装担当・レビュー担当の報告にある「提案」「申し送り」「未決」を1件ずつ着地させる。** 行き先は現タスクの修正か、台帳への追記。**報告に書かれただけのものは消える** — 会話は残らず、次のセッションが読むのは台帳と git だけ。着地させないと決めたなら、その判断を報告に書く
   - **申し送りの書式**: **行き先は未着手タスクに限る**(完了済みタスクに書き足しても誰も読まない。該当が無ければ新設する)。その `#### 内容` か `#### DoD` に1行足し、**行末に出所ラベル `(出所: <元タスクID> レビュー)` を必ず付ける** — 着手時に「この行はどこから来たのか」を辿れるようにし、`grep '出所:'` で残っている申し送りを一覧できるようにするため
   - **新規タスクを起こす条件**: **まず起こさずに済まないかを見る**(既定の行き先は現タスク)。送ると決まったら、①既存タスクの `#### 内容` / `#### DoD` に1行足すのが第一選択 ②どの既存タスクにも属さないものだけ新設する ③複数の申し送りはまとめて1タスクにしてよい。**タスクを細かく割らない** — 論理変更の単位で起こしていくと台帳が際限なく膨らむ
   - **仕様の側を直す必要が出たら、このループでは直さず `/spec-change` へ回す**(版数を指す参照箇所と台帳への追従が要るので、コミット1つでは閉じない)
   - タスク台帳の該当タスクを `- [x]` に更新する

7. **セルフレビュー**: `/self-review` を実行する。**呼ばれるのを待たない。** 作った成果物の種類から読み返すルールが決まるので、それを自分の出力に当てる。指摘が出たら直してから次へ進む。
   - **hooks が使えない環境では、ここが規則を自分の出力に当てる唯一の機会になる。** hooks が使えるなら、機械的に強制する検査を別に置ける — その場合もこの工程は残す(hooks が見るのは実行できる検査だけで、文章や網の妥当性は見ない)
   - 実装担当が書いた分だけでなく、**手順5で自分が直した分と、手順6で自分が書いた台帳・決定記録の文章も対象**

8. **着地させる**。
   - 変更一式を1コミットにまとめる(何を・なぜ)
   - **着地の仕方をこのスキルに埋めない** — 手順2(ブランチ命名)と同じ要領で、プロジェクトの規約(開発ワークフローの文書・貢献ガイド)から読み取って**そちらに従う**。マージまでを規約が定めているならマージまで行う
   - **読み取れなければ「push して MR/PR を作り、止まる」**(既定)。不可逆な操作を含まない側に倒してあり、マージが要るなら人が足せる。テンプレートがあればそれに沿って埋める(テンプレートの所在も規則も、同じくリポジトリから読み取る)
   - **レビュー担当の合格は、マージの承認ではない。** 人のレビューへ出せる状態になったことの判定でしかない。規約がマージまで含んでいる場合、マージしてよい根拠はその規約であって、合格判定ではない
   - `/loop` で回している場合も、ここで次のタスクへ進んでよい。**ただし直前のタスクと同じファイルを触るタスクは、前の変更が本流へ取り込まれるまで着手しない** — 未取り込みの変更の上に積むと、レビューの単位が崩れる
9. **報告**: 完了タスクID・要点・作成した MR/PR・次に着手予定のタスクIDを簡潔に報告する。行った操作は明示的に書く。

## 注意

- 判断に迷ったらプロジェクトのワークフロー文書(エスカレーション規則・事前に決めた実装詳細)に従う
- 台帳の書式を壊さない。タスクの削除禁止
- 1実行1タスク。まとめて複数消化しない(レビュー粒度を保つため)
