# self-review — 報告前の自己レビュー

**起動条件: 完了報告の前に必ず。** 呼ばれるのを待たない。

**モデルの階層で出し入れしない。** 「自分は上位モデルだから自前でやっている」という判定は内省に依存するが、**規則を読んでいたのに自分の出力へ当てていない**という失敗は階層を問わず起きる。一度読んだ状態と、この成果物に当てた状態は、内側からは区別できない。

**これは開放的な再検証ではない。** 手順2の表で読む対象が決まり、各行は2〜3節。「もう一度全部確かめろ」ではなく「この節を読んで、自分の出力に当てる」で終わる。

**引数**: 比較ベース(省略時は未コミットの作業ツリー、引数があれば `<base>...HEAD`)。

## 手順

### 1. 何を作ったかを確定する

`git diff`(または `git diff <base>...HEAD`)を**全読み**する。飛ばし読みしない。300行を超えるならコミット分割の余地を最後に指摘する。

**成果物は diff に出るものだけではない。** この作業中に自分が行った調査(grep で数えた・一覧を作った)と、**これから書く報告**も成果物に数える。どちらも diff には残らない。

### 2. 成果物の種類から、読み返すルールを決める

**表は下限。引いた行は必ず読む。** 「今回は関係ない」で外さない — ルールを外したときと同じ盲点が、その「関係ない」という判定に現れる。

**そのうえで、他に照合すべきルールが思い当たれば足す。** 判断で**足す**のは自由で、禁じているのは判断で**減らす**こと。表は網羅ではなく、拾い漏らしを防ぐ下限。

| 作ったもの | 該当の判定 | 読み返す |
|---|---|---|
| **常設ドキュメント**(規範・仕様・手順書・README・エージェント定義・スキル) | diff | `working-norms.md` の「書き方の規約」全体 / 「同じ事実に正を2つ作らない」 / 「書く場所は情報の寿命と適用範囲で決める」 |
| **コード** | diff | `01-engineering-principles.md` §5-1 必ず確認するケース / §5-2 変更耐性 / §5-3 テストの実効性 / **§5-4 コードを変えたときの完了条件** / §6 レビュー基準 |
| **掃引・検査・網**(grep で数えた / 一覧を作った / 「全部見た」と書いた) | diff、および**この作業中に自分が行った調査**(diff に残らない) | `working-norms.md` の「『全部見た』と言う前に、それを数えた網の妥当性を先に確かめる」 |
| **人へ向けた報告** | **常に該当**(このスキルは完了報告の前に走るので、報告は必ず書く) | `working-norms.md` の「読み手へ向けた報告は…」 / 「変更を報告するときは、読み手がその差分へ到達する手段を添える」 |

**常設ドキュメントには、表に加えて次を必ず当てる。** **作業の途中で分かった事実が、それより前に書いた記述を否定していないか**を最後に1度見る — 規範・手順書・仕様・タスクには**レビュアーもテストも無く**、書いた時点で正しければ後から嘘になっても誰も検出しない。コードはレビューとテストが別の目になるので、この確認は常設ドキュメントにだけ課す。

### 3. 読んだルールを、自分の出力に1件ずつ当てる

**ルールを知っていることと、この成果物に当てたことは別。** 節を読んだら、その節が要求している形になっているかを、実際の出力を見て確かめる。

- **文章なら**、書いた段落を読み直す。1段落が1つの主題か。見出しの1文だけで向きが決まるか。他所から引き継いだ文が、変更後の文脈でも意味を持つか
- **構造を変えたなら**(節を足した・分割した・移した)、**その構造を参照している箇所の意味が変わっていないか**を確かめる。節番号・「上の表」「下の節」のような相対参照が指す先が動く
- **見出し・導入文・表の列名が主張していることを、その配下の全項目が満たしているか**を確かめる。1項目でも外れていたら、直すのは項目ではなく主張の方かもしれない
- **掃引したなら**、使った検索語で拾えない書き方を1つ挙げられるか。挙げられるなら網を直してから数え直す

### 4. 種類を問わず見る

- **変更ファイルを列挙し、1ファイル1行で「なぜ変えたか」を書く。** 書けないファイルは意図しない混入 — 依頼スコープ外なら revert 候補として挙げる
- **debug 残骸を grep する**: 言語相当の出力文(`console.log` / `print(` / `debugger` / `fmt.Println` 等)、コメントアウトされたコード塊、条件のない `TODO`(「何を・どうなったら」がないもの)
- **交差するものとの両立**: この変更が触るものと交差する既存のものを列挙し、1件ずつ確認する。**コードだけの話ではない** — 文書なら、その記述を参照している別の文書が矛盾していないか。diff を眺めるだけでは出ないので、必ず既存側を読む

コードの観点(変更耐性・テストの実効性・契約変更の波及)は、手順2の表がコード行で読ませる `01-engineering-principles.md` §5・§6 が持つ。**ここに書き写さない。**

### 5. 指摘があれば直してから、1 に戻る

修正しないと決めた指摘は、理由を添えて残す。

## 出力

1. **指摘リスト**(重要度順。各項目は「場所 / 何が問題 / どうするか」)
2. **この変更で壊れうる最悪のケース1件**(必ず挙げる)
3. **手順2で引いた行と、読み返した節**(何を当てたかを示す)

## 注意

- 「自分が書いたもの」というバイアスを外し、**他人の成果物を読むつもり**で読む
- **指摘ゼロで通過することは稀。** ゼロなら読み方が浅い可能性を疑い、手順3(読んだルールを実際に当てる)に戻る
- レビューの順序を逆にしない。順序と基準は `01-engineering-principles.md` §6
- **この手順が減らせるのは「そもそも当てなかった」分だけ。** 読んで意味を確かめずに通せば同じことが起きる。最後の砦はレビュー担当と人
