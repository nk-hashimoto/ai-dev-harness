# bug-hunt — バグ原因特定の定型手順

**原因を説明できるまで直さない。** 「なぜかこれで直った」は直っていない。

**引数**: バグの症状(観測された挙動と、期待される挙動)。

## 手順

1. **再現手順を確立し、最小化する**。データを減らす・手順を減らす・依存を外す。再現できないバグは、直せたかどうかも判定できない。再現できない場合は、まず観測手段(ログ・計測)を足すのが先で、修正に進まない。
2. **「最後に動いていた状態」を特定する**。`git log` で関連ファイルの変更履歴を見る。範囲が広いなら `git bisect`(勘より速い)。
3. **仮説→検証のループを回す**:
   - 仮説を**1文で書く**。書けないならまだ観測が足りない → 観測に戻る。
   - その仮説を**検証するために**ログ・アサーション・一時テストを入れる(闇雲に散らばせない)。
   - 観測結果で仮説を更新する。
   - **3回外したら手を止める**。現在の仮説 / 観測事実 / 仮説と矛盾する事実 を書き出して再構成する(`~/.claude/norms/00-priority-rules.md` P10)。
4. **原因を説明できたら、テスト先行で直す**(`/test-first-fix`):
   - バグを再現する最小のテストを書く → 実行して **red を確認** → 修正 → green。
   - red にならないテストはバグを捉えていない。再現条件の理解が誤っているので手順1に戻る。
5. **横展開する**。原因のパターン(同じ誤った API 使用、同じ nullable の扱い漏れ、同じ境界条件)を grep し、同型のバグを探す。**バグは群れで存在する。**
6. 手順3で入れた一時的なログ・デバッグコードを**全て消す**。

## 出力

1. 最小再現手順
2. 原因の説明(**なぜ起きるか**。「どこを直したか」ではない)
3. 再現テスト(red → green の確認結果つき)
4. 修正
5. 横展開の検索結果(検索語と、見つかった/見つからなかった同型箇所)

## 注意

- **修正とリファクタリングを混ぜない。** 直す過程で気づいた汚さは別コミット・別提案に回す。
- 症状に絆創膏を貼るのではなく、不正な状態がそもそも作れない構造にできないかを一度考える。ただしスコープは最小に(P6)。
- `catch` で握りつぶして症状を消すのは修正ではない。無視してよい理由をコメントで書けないなら、握りつぶさない。
