# spec-check — 実装と仕様の整合レビュー

**引数**: 仕様書のパス(+対象セクション)、検証対象の実装(ブランチ / ディレクトリ / 機能名)。省略時は、プロジェクトの CLAUDE.md・README から「正の仕様」を特定する。

## 手順

1. **正の仕様とそのバージョンを確定する**。ファイルのバージョン表記と `git tag` / `git log` を確認し、実装がどの版を前提にしているかを押さえる。正が複数あって食い違うなら、**そこで止めて矛盾を報告する**(P1)。
2. **検証可能な主張を抽出する**。仕様の該当セクションから「X のとき Y になる」の形に落ちる文をリスト化する(番号を振る)。落ちない文(理念・背景)は対象外として分ける。
3. **各主張に対応する実装とテストを探す**。判定は3値:
   - **一致**(根拠のファイル:行を添える)
   - **不一致**(実装の実際の挙動を添える)
   - **未実装 / 未確認**(まだ書かれていない、または対応箇所を特定できない)
4. **逆方向も見る**。実装にあって仕様にない挙動(undocumented behavior)を検出する。特に: エラー時の振る舞い、既定値、上限・下限、暗黙の並び順、race 時の勝者。
5. **仕様書内の矛盾**を報告する。同じ対象について別セクションが違うことを言っている箇所、決定記録(D-N 等)と本文が食い違う箇所。

## 出力

| # | 仕様の主張 | 判定 | 根拠 / 実際の挙動 |
|---|---|---|---|

に加えて:
- undocumented behavior の一覧
- 仕様書内の矛盾の一覧
- 各不一致について「仕様側が古いのか、実装が誤りなのか」の**両論併記**

## 注意

- **不一致を見つけても、どちらが正かを自分で決めない。** 特に「実装に合わせて仕様を書き換える」を無断でやらない。両論併記でユーザーに返し、決まってから直す。
- 仕様のバージョンを必ず確認する。古い版を見て「不一致」と報告するのが最も多い誤検出。
- このスキルは検出まで。修正は別タスクとして起票する(決定を伴うなら `/decision-log`)。
